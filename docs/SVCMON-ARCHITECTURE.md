# 성능점검 — 아키텍처 / 용량 산정 / 튜닝

1만 대 이상 서버, 일 2GB 이상 로그를 전제로 설계한 성능점검(svcmon) 모듈의 구조와 실측값,
튜닝 방법을 정리한 문서입니다. 점검 유형별 상세는 [SVCMON-TESTS.md](SVCMON-TESTS.md),
대량 등록·CSV 는 [SVCMON-BULK.md](SVCMON-BULK.md).

---

## 1. 왜 독립 모듈인가

성능점검은 포탈 코어(vCenter 수집·인벤토리·알림)와 **코드·데이터·실행 스레드가 모두 분리**되어 있습니다.

| 축 | 분리 방식 |
|---|---|
| 실행 | `worker_threads` 풀에서 점검 수행 — 메인 이벤트 루프를 침범하지 않음 |
| 데이터 | `CONFIG_DIR/svcmon.json`(대상·폴더·정렬) 전용. 포탈 스냅샷·시계열 DB와 무관 |
| 로그 | `CONFIG_DIR/svcmon-logs/*.csv` 전용 디렉터리 |
| 설정 | `CONFIG_DIR/svcmon-log.json` 전용 |
| 킬스위치 | `SVCMON_ENABLED=false` → 폴러 미기동(포탈 나머지는 정상) |

이유: 점검 항목이 수만 개로 늘어도 포탈의 vCenter 수집 주기(30초)와 API 응답이 흔들리면 안 됩니다.
CLAUDE.md 의 "매 폴링 주기마다 이벤트 루프를 블로킹하는 동기 작업 금지" 원칙을 이 모듈에도 적용했습니다.

```
 [메인 스레드]                              [워커 스레드 × N]
 poller(5초 틱)                             ┌─ checker: ping/tcp/http/… 실행
   ├ 만기 인덱스에서 due 추출  ──postMessage─▶│   sockLimit 세마포어(256) — 소켓 대기형
   ├ 결과 반영(청크 500 + setImmediate 양보)  │   procLimit 세마포어(64)  — ping/trace(CLI)
   └ CSV 버퍼 push(O(1))       ◀──results───└─ 상태 없음(죽어도 재생성만)
        ↓ 200ms / 256KB 배치
   WriteStream → svcmon-logs/results-*.csv
```

## 2. 부하 병목을 없앤 5가지 결정 (모두 실측 근거)

### ① 만기 인덱싱 — 전수 스캔 제거
매 틱에 전 항목을 순회하면 10만 항목 × 5초틱 = **초당 2만 회 비교**입니다.
`nextDue`(항목별 다음 실행 시각) 맵을 두고 만기된 것만 꺼냅니다. 인덱스는 저장소 리비전이
바뀔 때만 재구성합니다(`storeRevision()`).

### ② 동시성을 두 갈래로 분리
- **소켓 대기형**(tcp/http/dns/배너 등): CPU 를 거의 쓰지 않으므로 크게 열어야 처리량이 나옵니다
  → `SVCMON_CONCURRENCY` 기본 **256**/워커.
- **프로세스 생성형**(ping/trace): CLI 를 spawn 하므로 과하게 열면 시스템이 먼저 무너집니다
  → `SVCMON_PROC_CONCURRENCY` 기본 **64**/워커.

실측: 단일 세마포어 32 → 두 갈래(256/64) 변경으로 동일 부하 **146초 → 32.7초(4.5배)**.

### ③ 파이프라인 분배 — 웨이브 유휴 제거
초기 구현은 "워커 수만큼 보내고 전부 끝나길 기다림"이라 웨이브마다 가장 느린 배치를 기다렸습니다.
지금은 각 워커가 배치를 끝내는 즉시 다음 배치를 집어갑니다(작업 큐).

### ④ 결과 반영 청크 양보
수천 건 결과를 한 루프로 반영하면 그 동기 루프가 이벤트 루프를 막습니다.
실측 **메인 루프 최대지연 57ms** → 청크 500 + `setImmediate` 양보 후 **3ms**.

### ⑤ CSV 는 스트림 배치 + 백프레셔
`appendFileSync` 를 결과마다 호출하면 초당 수천 건에서 즉시 붕괴합니다(동기 write + fsync).
링버퍼에 담아 **200ms 또는 256KB** 단위로 `WriteStream` 에 flush 하고, `write()` 가 false 면
`drain` 까지 대기합니다. 버퍼가 32MB 를 넘으면 **오래된 행부터 폐기**하고 카운트합니다
(로그 때문에 점검이 밀리는 것이 더 나쁨 — 폐기 수는 설정 화면에 표시).

## 3. 실측 결과 (2026-08-07, macOS / Node 24 / 4워커)

| 항목 | 측정값 | 조건 |
|---|---|---|
| 대상 1만 개 × 항목 3개 등록 | **74ms** (항목 3만) | `bulkAddTargets` 1회 저장 |
| 저장 파일 크기 | 5.1 MB | 대상 1만 + 항목 3만 |
| 처리량 — 정상 응답 | **249 건/초** | TCP 즉시 응답, 4워커 × 256 |
| 처리량 — 전부 무응답(최악) | **122 건/초** | 4초 타임아웃 100%, 4워커 |
| 메인 루프 최대지연 | **3ms** | 4천 건 처리 중 10ms 타이머 관측 |

## 4. 용량 산정식

```
초당 필요 처리량 = 전체 점검 항목 수 ÷ 평균 주기(초)
초당 가능 처리량 ≈ 워커 수 × SVCMON_CONCURRENCY ÷ 평균 응답시간(초)
```

**예시 — 1만 대 × 항목 3개 = 3만 항목**

| 주기 | 필요 처리량 | 4워커(249/s) | 8워커(약 500/s) |
|---|---|---|---|
| 60초 | 500/s | ✗ 부족 | ✓ 가능 |
| 120초 | 250/s | ✓ 경계 | ✓ 여유 |
| 300초 | 100/s | ✓ 여유 | ✓ 여유 |

**권장 구성**
- 1만 대까지: 주기 **120~300초** + `SVCMON_WORKERS=6~8`(vCPU 8 기준)
- 그 이상 또는 고RTT 사이트 포함: **엣지 노드에 분산**(DC 별 엣지가 자기 대역을 점검)
- ping 비중이 높으면 `SVCMON_PROC_CONCURRENCY` 를 올리기보다 **TCP 점검으로 대체**하는 것이 안전

**로그 용량**
```
일 로그량 ≈ 초당 처리량 × 86400 × 98B
예) 250/s → 250 × 86400 × 98B ≈ 2.0 GB/일
```
일 2GB 이면 `rotate=day` + `maxFileMB=512` → 하루 약 4개 파일(-p01~p04),
`keepFiles=90` 이면 약 90일 = **180GB**. 디스크가 부족하면 `maxTotalMB` 로 상한을 두거나
`mode=changes`(상태 변화만 기록)로 바꾸면 로그량이 보통 **1/100 이하**로 줄어듭니다.

## 5. 환경변수

| 변수 | 기본값 | 설명 |
|---|---|---|
| `SVCMON_ENABLED` | `true` | `false` 면 폴러 미기동(점검 전체 중지) |
| `SVCMON_WORKERS` | `min(4, cpu-1)` | 워커 스레드 수. **0 이면 워커 미사용(인라인)** |
| `SVCMON_CONCURRENCY` | `256` | 워커당 소켓 대기형 동시 실행 수 |
| `SVCMON_PROC_CONCURRENCY` | `64` | 워커당 ping/trace(CLI) 동시 실행 수 |
| `SVCMON_BATCH` | `250` | 워커 1회 메시지에 담는 점검 수(직렬화 비용 제한) |
| `SVCMON_TICK_MS` | `5000` | 폴러 틱 간격 |
| `SVCMON_MAX_PER_TICK` | `4000` | 한 틱에 실행할 최대 항목 수(만기가 몰려도 폭주 방지) |
| `SVCMON_ROLE` | `both` | `central`=실행 안 함(배포·수신만) · `edge`=실행+보고 · `both`=단독(§8) |
| `SVCMON_PUSH_INTERVAL_MS` | `60000` | (엣지) 결과 push 주기. 하한 15초 |
| `SVCMON_PUSH_CHUNK` | `2000` | (엣지) 청크당 행 수. 413 수신 시 자동 절반(최소 250) |
| `SVCMON_CONFIG_PULL_MS` | `300000` | (엣지) 정의 pull 주기 |
| `SVCMON_EDGE_SILENCE_MIN_MS` | `300000` | (중앙) 무보고 판정 하한 — 실제 임계 = max(이 값, 3×엣지 push 주기) |
| `SVCMON_EDGE_MAX_AGENTS` | `64` | (중앙) 수신 엣지 수 상한 |
| `SVCMON_EDGE_MAX_ROWS` | `20000` | (중앙) 엣지당 보관 행 상한(초과는 카운터로 보고) |

상한값: 대상 20,000개 · 대상당 점검 200개 · 전체 점검 200,000개 · 폴더 5,000개 · 트리 깊이 10.

**1회 요청 상한**(저장소 상한과 별개, 라우트에서 강제): 대량 등록/CSV 가져오기 **2,000행**,
신규 점검 10,000개. 초과는 잘라내지 않고 **오류**로 돌립니다(절단하면 사용자가 누락을 인지하지
못합니다). 근거: 다양한 경로 5,000행 등록이 116ms 실측 → 2,000행 약 50ms. 본문 한도 1MB 에서
점검 행 약 150B 면 약 6,500행이 물리 한계입니다.

### 등록 시 용량 판정 (v2.243)

대량 등록·CSV 가져오기는 커밋 전에 "이 규모를 폴러가 소화할 수 있는지"를 계산합니다
(`svcmon/capacity.js`). 상수는 아래 §3 실측값에서 파생하고 워커 수는 실제 설정값을 읽습니다.

```
틱 천장 = SVCMON_MAX_PER_TICK ÷ (SVCMON_TICK_MS/1000) = 4000 ÷ 5 = 800/s
```

필요 처리량이 **틱 천장을 넘으면 400 으로 거부**합니다. 이 구간에서는 어떤 튜닝으로도 지정한
주기를 지킬 수 없고, `sweep` 이 만기 목록 앞부분에서 `MAX_PER_TICK` 개만 꺼내므로 뒤쪽 항목이
다음 틱으로 밀립니다 — **화면은 '주기 60초'라고 표시하는데 실제 주기가 조용히 늘어나는** 상태가
됩니다. ping·trace 는 프로세스를 띄우므로 소켓형과 **별도 상한**으로 판정합니다(소켓형 기준만
쓰면 ping 위주 등록이 통과해 버립니다).

## 6. 운영 점검 방법

```bash
# 폴러·워커·로그 라이터 상태(관리자 로그인 필요)
curl -s -H "Authorization: Bearer <token>" http://localhost:4000/api/svcmon/diag | jq

# 확인 포인트
#   poller.lastSweepMs  : 1틱 소요(주기보다 크면 처리량 부족 → 워커·동시성·주기 조정)
#   poller.lastCount    : 그 틱에 실행한 항목 수(maxPerTick 에 계속 붙으면 적체)
#   pool.inlineFallbacks: 0 이 정상. 늘어나면 워커가 죽고 있다는 뜻(로그 확인)
#   log.dropped         : 0 이 정상. 늘어나면 디스크 I/O 가 못 따라감(분할·모드 조정)
#   log.buffered        : 상시 수천이면 flush 가 밀리는 상태
```

**재현(부하 시험)**: 임시 `CONFIG_DIR` 을 만들고 `bulkAddTargets` 로 대량 등록한 뒤
`poller.runNow()` 를 1회 돌리며 10ms 타이머 지연을 관측하면 위 표를 재현할 수 있습니다.
`SVCMON_WORKERS=0` 으로 두면 워커 없이(인라인) 비교 측정할 수 있습니다.

## 7. 알려진 한계 (정직한 기록)

- **ping 은 CLI 프로세스 기반**입니다. 1만 대 전부 ping 을 걸면 `SVCMON_PROC_CONCURRENCY` 가
  병목이 됩니다(초당 약 16건/워커 = 64÷4초). raw 소켓 ICMP 나 `fping` 배치 실행은 미구현입니다.
- 결과는 **인메모리 최신값 1건**만 유지합니다(시계열 아님). 추이 분석은 CSV 로그를 외부 도구로
  집계해야 합니다. 상세 모달의 24H TREND 는 아직 자리만 있고 실데이터가 아닙니다.
- 실측은 **단일 macOS 개발기** 값입니다. 운영(RHEL9 · 8 vCPU)에서는 재측정을 권장합니다 —
  특히 무응답 비중이 높은 환경은 타임아웃이 처리량을 지배합니다.
- 로그는 CSV 만 지원합니다(SQLite 적재·집계 API 는 미구현).
- **알림 연동이 없습니다** — 임계 초과 시 Slack/Teams 발송이 이 모듈에 없습니다
  (`grep notify\|alerts server/src/svcmon/` → 0건). `server/src/alerts.js notify()` 가 이미 있고
  `net/monitor.js` 는 쓰는데 svcmon 만 빠져 있습니다. 점검 항목을 수만 개로 늘려도 사람이 화면을
  봐야 장애를 아는 상태이므로, 규모를 키우는 작업보다 **알림이 선행 요구**입니다.
- **`nextDue` 가 인메모리라 재시작마다 전 항목이 동시 만기**입니다(없는 항목은 즉시 만기로
  넣습니다). 자동 업그레이드가 상시 도는 제품이라 재시작은 정기 이벤트인데, 폴러 지터가 없어
  기동 직후 버스트가 발생합니다.
- **`svcmon.json` 이 백업에서 조용히 제외**됩니다. 백업 서비스의 파일 크기 상한(8MB)을 넘기면
  건너뛰는데, 15,000 대상 × 8점검 규모가 실측 16.4MB 였습니다. 그래서 CSV 가져오기에
  `replace`(기존 목록 최신화) 모드를 넣지 않았습니다 — 복구 경로가 없는 상태에서 최대 2만 대상
  삭제 기능을 주면 안 됩니다.
- **점검 일시중지(작업 창)가 없습니다.** 패치 창에 수천 점검이 한꺼번에 실패로 뒤집힙니다.
  알림을 붙이면 그대로 폭발합니다.
- ~~엣지 분산이 미구현~~ → **v2.245 에서 구현**(§8). 배정·실행 위임·결과 수신·무보고 감시까지.
  남은 것은 §8 의 '알려진 한계' 참고.
- `/state` 에 offset/cursor 가 없어 **한 폴더 2,000 대상 초과분은 조회할 수 없습니다**
  (`limit` 이 2,000 으로 클램프됩니다). 1회 등록 상한을 2,000 에 맞춘 이유이기도 합니다.

## 8. 엣지 위임 (RMA Active 방식, v2.245)

**모든 점검을 엣지(원격 법인)에서 실행하고 중앙은 정의 관리·결과 표시만** 하는 구조를
지원합니다. 고RTT 사이트(폴란드·미국동부 800ms+)를 중앙에서 직접 찌르면 RTT 가 응답시간
판정을 오염시키고, 점검 타임아웃이 코드 고정값이라 사이트별로 예산을 늘릴 수단이 없습니다 —
관측 위치를 대상 옆으로 옮기는 것이 유일한 정확한 해법입니다.

### 역할 (SVCMON_ROLE)

| 값 | 실행 | 용도 |
|---|---|---|
| `central` | **안 함** | 중앙 포탈. 정의를 관리해 엣지에 배포하고 결과만 수신·표시 |
| `edge` | 함 | 원격 법인 엣지. 중앙에서 정의를 받아 실행하고 결과를 push |
| `both` (기본) | 함 | 단일 사이트 설치(기존 동작). 기본값인 이유: 업그레이드로 기존 설치의 감시가 조용히 멈추면 안 됨 |

### 데이터 흐름

```
[중앙 SVCMON_ROLE=central]                     [엣지 SVCMON_ROLE=edge]
 배정 저장(트리 범위 → 스냅샷·sig)
   ─ GET /api/central/svcmon-config ──────────▶ 5분 주기 pull (sig 같으면 본문 생략)
                                                deleteTargetsByBatch(이전 태그)
                                                bulkAddTargets(새 목록, batch=central:<sig16>)
   ◀───────── POST /svcmon-config-ack ────────  적용 수 회신 (수가 정확히 일치해야 '활성')
                                                폴러가 로컬 실행 (틱 5초 · 워커 풀)
   ◀───────── POST /svcmon-report ────────────  60초 주기 push (전량 스냅샷 · 청크 2,000행)
 엣지 카드 표시 · 무보고 감시(3×주기) · 알림
```

### 설계 결정과 근거 (전부 실측)

- **push(Active)이고 pull(Passive)이 아닌 이유**: pull 의 공유 토큰은 기본 구성에서
  CENTRAL_TOKEN 과 같은 값이 되고(하나 유출 = 전 엣지), 기존 pull 응답은 `generatedAt`
  때문에 304 가 성립한 적이 없으며, pull 은 중앙 인바운드를 요구합니다(폐쇄망 불가).
  push 는 엣지별 **개별 토큰 전용**이며 저장 키는 토큰에서 해석한 이름만 씁니다
  (본문 agent 를 읽지 않음 — 남의 이름으로 위조 불가, 실측 403).
- **전량 스냅샷(델타 아님)**: 엣지 내부에서 항목이 밀리면 '여전히 ok'와 '안 돌았다'를
  델타로는 구별할 수 없습니다.
- **청크 2,000행**: gzip 은 본문 한도를 완화하지 않습니다(한도는 해제 후 크기, 실측 413).
  413 은 재시도 대상이 아니므로 엣지가 청크를 절반으로 줄여 재시도합니다.
- **시각은 중앙 시계**: 행마다 구간값(측정 후 경과 ms)만 싣고 중앙이 환산합니다. 엣지
  시계가 틀려도 판정이 흔들리지 않고, 비정상 구간값(음수·24h 초과)은 수신 시각으로
  대체하고 카운트합니다.
- **배포 태그 24자**(`central:<sha1 16>`): store 가 batch 를 40자로 자르므로 48자 태그는
  삭제가 0건이 되어 정의가 영구히 갱신되지 않습니다(실측).
- **ack 기반 handoff**: 등록 함수는 실패에 예외를 던지지 않고 조용히 0건을 돌려줄 수
  있으므로, 엣지의 적용 수가 배정 수와 **정확히 일치**해야 '활성'입니다. 불일치는
  화면에 그대로 노출합니다(조용히 넘기면 그 차이만큼 감시 공백).
- **무보고 판정 = max(3 × 엣지 push 주기, 5분)**: 항목 0개 엣지도 봉투(하트비트)를
  보내므로 '항목 없음'과 '죽음'이 구별됩니다. 무보고 엣지의 점검은 정상으로도 장애로도
  세지 않고 **알 수 없음**으로 표시합니다. 전환 시에만 알림(복구 포함), 첫 관측은
  기준점만 잡습니다(중앙 재시작마다 알림 폭발 방지).
- **기본 제외 유형**: `trace`(traceroute 부재 환경 전면 실패)·`domain`(whois 는 외부
  인터넷 필요)은 기본으로 엣지에 보내지 않습니다(배정에서 해제 가능).
- **ping 판정 방식 보고**: ping CLI 가 없는 엣지는 TCP 연결 폴백으로 **판정 의미가 바뀐
  채** 동작합니다. 이 사실은 워커 스레드 안에서만 관측되므로 워커가 결과와 함께 올려
  보내고, 엣지 카드에 'ping=TCP 폴백' 배지로 표시합니다.
- **중앙 폴백은 만들지 않았습니다**: 엣지가 죽었을 때 중앙이 대신 점검하면 타임아웃
  예산이 달라 '엣지 장애'가 '대상 장애'로 오역됩니다. 감시 공백은 숨기지 않고
  '알 수 없음'으로 드러냅니다.

### 알려진 한계 (정직한 기록)

- **중앙 수신 상태는 디스크에 남지 않습니다.** 중앙 재시작 후 다음 push(기본 60초)까지
  전 엣지가 무보고로 보입니다. 48MB 규모(30엣지×5,000행)의 동기 직렬화를 5초 디바운스로
  반복하는 비용이 더 크다는 판단이며, '오래된 정상을 초록으로'보다 안전한 쪽입니다.
- **개별 점검의 정상→실패 전이 알림은 없습니다.** 무보고 알림만 있습니다.
- 배정 삭제는 엣지의 기존 정의를 지우지 않습니다(원격에서 감시를 임의로 끊지 않음).
  엣지 정리는 그 엣지에서 배치 태그로 직접 합니다.
- streak(연속 횟수)은 엣지 재시작 시 1 로 리셋됩니다(엣지 results 가 인메모리).
