# Backup 현황 › 백업 실행 (v2.818)

메뉴: **서버 › Backup › 백업 실행** 탭(Summary · Detail · EM 옆) · 도구 키 `backup-run` · admin 전용.
Detail 화면에서 VM 을 고르고 **'Veeam 백업 실행 →'** 을 누르면 고른 VM 을 가지고 이 탭으로 온다.

포탈에서 고른 VM 을 Veeam Backup & Replication(VBR) REST API 로 백업한다. 포탈은 백업 소프트웨어가 아니다 —
요청을 보내고 Veeam 의 세션 결과를 읽어 보여 줄 뿐이다. 백업 데이터·보존·저장소는 Veeam 이 관리한다.

## 무엇을 다시 쓰는가(새로 만들지 않은 것)

- **Veeam 서버 등록**: 설정 › Veeam 백업 서버(모니터링 등록부 `veeam-servers.json` — 주소·계정·담당 엣지·연결 vCenter). 백업 실행용 등록은 따로 없다.
- **보호 상태**: Backup 현황과 같은 대조 코어(`veeam/parse.js matchToVcenter` — moref 는 vCenter 이름과 함께, 이름 일치는 같은 vCenter 안에서만).
- **인증 정지**: 모니터링 폴러와 같은 기록(같은 계정이다). 정지 중이면 백업 요청·세션 확인을 보내지 않는다. 비밀번호를 고치면 풀린다.
- **장비 인증서 신뢰**: 모니터링과 같은 판정(설정 › Security › 장비 신뢰에서 승인한 지문).

## 정직 기록 — 실제 VBR 로 확인하지 못한 것

v2.818.0 까지 쓰기 요청은 실제 VBR 로 확인하지 못했다(개발 환경에 VBR 이 없다). **2026-10-29 현장 첫 실행**(VBR 'OC2', 포탈 전용 잡 1대 — 실행 기록 화면)으로
아래 표의 '현장 확인' 항목이 확인됐다. VBR 버전·API 판은 기록에 없다(등록부 기본 1.1-rev0 추정).

| 항목 | 근거 | 상태 |
|---|---|---|
| 토큰·`x-api-version`·잡 목록·세션 읽기 | 모니터링 모듈(`veeam/client.js`)과 같은 방식 — 그 모듈 주석에 실서버(VBR 12.3) 응답 기록이 있다 | 확인(모니터링 기록 기준 — 이 기능으로 다시 확인하지는 않았다) |
| 잡 시작 `POST /api/v1/jobs/{id}/start` · 본문 `{performActiveFull:false}` | 현장 기록 `start:body` | **현장 확인**(OC2) — 시작 응답에서 세션 id 도 읽혔다 |
| 잡 VM 지정 `virtualMachines.includes[]` | 현장 기록 | **현장 확인 — flat**(`{type,hostName,name,objectId}`). `inventoryObject` 래퍼는 OC2 가 400 `'Name'·'Type'·'Host Name' must not be empty` 로 거절 → v2.818.1 부터 flat 을 먼저 보낸다 |
| Quick Backup 은 API 1.2-rev0 부터 · 전체 복원 지점이 있는 VM 만 | 'New Features 1.2-rev0' · 사용자 가이드 | 확인(문서) |
| Quick Backup 경로 `POST /api/v1/jobs/quickBackup/vSphere` 와 본문 | 공개 자료로 확정 못 함 | **추정** — 후보 3개(A `{virtualMachines:[…]}` · B `{objects:[…]}` · C VM 마다 하나)를 차례로, 쓴 후보를 실행 기록 '요청 형태' 에 남긴다 |
| 잡 생성 본문(type·저장소·보존·스케줄) | 현장 기록 `create:Backup:flat` | **현장 확인** — type `Backup` + flat 이 생성됐다(다른 VBR 판은 남은 후보로) |
| 세션 읽기(`/sessions/{id}` — 상태·결과) | 현장 기록(결과 Success) | **현장 확인** |
| 진행 상세(v2.822.2 — 작업·세션의 creationTime·endTime · progress.processedSize·readSize·transferredSize) | 모니터링 모듈과 같은 후보 이름 | **추정** — 못 읽으면 '—'(0 을 만들지 않음). 평균 속도는 처리량 ÷ 경과로 포탈이 계산한 값 |
| 세션의 VM 별 작업(`/sessions/{id}/taskSessions`) | 현장 기록 | **현장에서 실패 — 사유 미상**. v2.818.1 부터 실패 사유를 실행 기록에 남긴다(다음 실행에서 확인) |
| 필요한 Veeam 계정 최소 역할 | — | 확인 못 함 |

첫 실사용에서: 실행 현황의 **요청 형태**(variant)와 그룹 메모(거절된 후보)를 보고 후보를 좁힌다.

## 백업 방식

- **빠른 백업(Quick Backup)** — VM 이 속한 기존 잡의 설정으로 그 VM 만 증분 백업. 그 VM 을 백업한 B&R 서버로 보낸다.
- **포탈 전용 잡** — vCenter 마다 `<접두><vCenter 이름>-<vCenter id 해시 6자리>` 잡을 만들거나 VM 을 넣고 잡을 시작한다.
  - 잡 설명의 표지 `[vmware-portal:managed]` 가 있는 잡만 고친다. 같은 이름이라도 표지가 없으면(사람이 만든 잡) 손대지 않는다.
  - 처음 들어간 VM 은 전체 백업부터. **잡을 시작하면 그 잡의 VM 전부가 함께 돈다**(이미 들어 있는 VM 은 증분).
  - 저장소·보존은 백업 실행 설정에서 Veeam 서버마다 정한다. 잡은 스케줄 없이 만든다. 잡에 들어간 VM 은 Veeam 라이선스를 소비할 수 있다(일반 과금 기준 추정 — 계약 확인).
  - 이름에 해시를 붙이는 이유: 한글 이름은 글자를 걸러 내면 비어서 두 vCenter 가 같은 잡을 쓰게 된다. 이 형식을 바꾸면 이미 만든 잡을 못 찾는다.

## 실행 상태(표의 '실행 상태')

| 상태 | 뜻 |
|---|---|
| 보호됨 · Quick 가능 | 복원 지점(개수를 모르는 '있음' 포함)·마지막 백업 근거가 있고, 그 백업을 한 B&R 서버가 등록부에 있다 |
| 에이전트 백업 포함 | 게스트 에이전트 백업(컴퓨터 이름으로 맞춘 것)이 섞여 VM 단위 백업인지 모른다 — Quick 은 보내지 않고, 포탈 전용 잡 방식을 고르면 보낸다(v2.820.1) |
| 다른 서버(미등록) | 백업 근거는 있지만 그 Veeam 서버가 B&R 로 등록돼 있지 않다(EM 으로만 보임 등) — 보내지 않는다 |
| 복원 지점 없음 | 잡에는 있지만 복원 지점이 없다 — Quick Backup 불가 |
| 미보호 | 대조 결과를 읽었고 Veeam 에 이 VM 이 없다 |
| 확인 불가 | 그 vCenter 를 맡는 B&R 서버 결과를 **전부** 읽지 못했거나 그중 하나라도 오래됐다(수집 주기 2배 + 2분 — 화면의 '백업 중' 신선도와 같은 식) — 미보호로 단정하지 않고 **어느 방식으로도 보내지 않는다** |
| 연결 서버 없음 | 그 vCenter 를 맡는 B&R 서버가 등록돼 있지 않다 |

Veeam 이 그 vCenter 를 부르는 이름(잡 includes 의 hostName): 직접 지정 > 대조가 배운 별칭(하나일 때) > 포탈 등록 주소. 화면이 무엇을 쓰는지 보여 준다.

## 진행 상세 · VM 크기(v2.822.2)

- 포탈 백업 VM 표: VM 크기(사용 · 할당) 열과, 상태 아래 한 줄 진행 요약(진행률 · 처리량/할당 · 경과 · 평균 속도(계산)). '세부 보기' 로
  시작 · 경과 · 처리/읽음/전송 · Veeam 세션·작업 상태와 메시지 · 요청·세션 id 를 펼친다. Veeam 에 따로 묻지 않는다 — 세션 추적이 이미 읽는 응답에서 꺼낸다.
- 여러 VM 을 담은 세션에서 그 VM 의 작업 값을 못 읽으면 세션 전체 값을 쓰고 '(세션 전체)' 라고 표시한다.
- VM 크기: 사용 = vCenter `summary.storage.committed`(스냅샷·스왑 포함), 할당 = committed + uncommitted(둘 다 읽었을 때만). VM 선택 표·미리보기 합계(크기 모르는 VM 은 더하지 않고 센다)·실행 기록에 같은 값.

## 실행 결과

- 성공 · 경고 · 실패 — Veeam 세션(VM 별 작업)이 말한 결과. VM 하나만 담은 세션(복원·VM 별 Quick)은 세션 결과가 곧 그 VM 의 결과다(작업 목록에 그 이름이 없어도 — v2.820.1). 포탈 전용 잡 세션은 잡의 다른 VM 도 돌아 그렇게 보지 않는다.
- **확인 불가** — 성공도 실패도 아니다: 요청이 Veeam 에 닿았는지·끝났는지 모른다(전송 오류·시한·5xx·엣지 미회신·세션 id 없음·24시간 초과).
  포탈은 **다시 보내지 않는다**(이중 백업 방지) — Veeam 콘솔에서 확인한다.
- **보내지 않음** — 확실히 보내지 않았다(인증 정지·시한 지남·엣지가 가져가지 않음·건너뜀 설정).
- 같은 Veeam 서버로 진행 중인 요청이 있으면 새 요청은 409. 포탈이 재시작하면 '보내던 중' VM 은 확인 불가로 닫고, 세션을 받은 VM 은 추적을 잇는다
  (복구는 실행 기록 파일을 **처음 읽을 때만** — 기동 뒤 이 프로세스가 시작한 실행은 건드리지 않는다).
- 세션 추적이 계속 실패하면(세션 경로 추정이 틀렸거나 서버를 껐거나 인증 정지) 그 서버의 새 요청이 시한까지 막힌다 — 실행 현황의 **기록 닫기**(OTP · 감사)로
  포탈 기록만 닫는다(끝나지 않은 VM 은 확인 불가). Veeam 의 세션·잡은 멈추지 않는다.
- 2xx 를 받은 뒤 본문 읽기가 끊기거나 JSON 이 아니면 '받아들였으나 세션 id 모름'(확인 불가)이다 — 실패로 적지 않는다(다시 눌러 두 번 도는 것을 막는다).
- Quick Backup 후보 C(VM 마다 요청)는 VM 마다 독립이다 — 한 VM 의 거절·응답 없음이 다른 VM 의 요청이나 받은 세션을 버리지 않는다.

## 담당 엣지가 있는 Veeam 서버

그 엣지가 5초마다 `GET /api/central/veeam-run-ops` 로 자기 몫을 가져가 현지에서 보내고 `POST /api/central/veeam-run-result` 로 회신한다(엣지별 개별 토큰 전용).
작업에는 **비밀번호가 없다** — 엣지는 중앙이 이미 배정해 둔 자기 등록부 사본으로 로그인한다. 시한은 남은 시간으로 받아 엣지 시계와 무관하다.
엣지가 2분 안에 가져가지 않으면 '보내지 않음', 가져간 뒤 시한 안에 회신이 없으면 '확인 불가'.

## 안전장치

- 백업 실행·설정 저장은 OTP 재인증(OTP 가 없는 계정은 설정 소유자만) + 감사 로그. 설정은 전체 범위 관리자만.
- VM 목록·실행은 사용자 범위(조회 밖 404 → 쓰기 밖 403). 실행 기록은 VM 이 전부 자기 범위인 것만 보인다.
- 실패·모름 요청을 자동으로 다시 보내지 않는다. 후보 체인은 서버가 '모양을 모른다'(400·404·405·415·422) 고 답할 때만 다음 후보로 간다.
- 인증 정지 중이면 저장소 목록 조회도 보내지 않는다(같은 계정 — 반복 클릭이 계정을 잠그지 않게).

## 포탈 백업 관리(v2.819)

포탈로 백업한 VM 을 포탈에서 관리한다. 들어가는 곳 두 군데(같은 관리 창):
- **vCenter 상세 › VM 폴더 트리** — 포탈로 백업한 VM 에 **Portal** 배지(✓ 성공 · ! 경고 · ✕ 실패 · ? 확인 불가 · 백업 중 · 잡에서 뺌 · 삭제됨 + 마지막 요청 날짜).
  배지를 누르면 관리 창. 폴더 줄의 **이 폴더 백업** 은 그 폴더(하위 포함) VM 을 백업 실행 화면으로 가져간다(200대까지 — 보내기 전에 미리보기·OTP).
- **Backup › 백업 실행 › 포탈 백업 VM** 표 — VM · vCenter·폴더 · 방식 · 마지막 요청 · 상태 · 최근 복원 · 관리.

관리 창:
| 기능 | 하는 일 | 안전장치 |
|---|---|---|
| 복원 지점 | Veeam 에 직접 묻는다(창을 열 때 1회 · 다시 읽기 버튼) — 만든 시각 · 백업(잡) · 포탈 잡 · 이 VM 확인 방식 | 읽기만. 이름으로 찾은 뒤 **백업 개체의 moref·vCenter(hostName·path 첫 마디)** 가 맞는 지점, 확인할 수 없으면 **이 vCenter 의 포탈 전용 잡** 지점만 보인다. 다른 vCenter 의 같은 이름 VM 백업은 숨기고 개수만 말한다(반증 F1) |
| 새 VM 으로 복원 | 고른 복원 지점을 **새 이름의 VM** 으로 원래 ESXi 호스트에 **전원 꺼진 채로** | 원래 위치(덮어쓰기)는 없다(코드에 type `Customized` 하나 — 테스트가 고정). 새 이름이 그 vCenter 의 VM 이름·최근 복원 요청 이름과 겹치면 409. 보내기 직전에 서버가 지점을 목록과 같은 판정으로 다시 묶는다(다른 vCenter 지점이면 보내지 않음). OTP · 감사 |
| 포탈 잡에서 빼기 | 포탈 전용 잡(표지)에서 그 VM 을 뺀다 — 이미 만든 복원 지점은 Veeam 보존 정책대로 남는다 | 표지 없는 잡은 고치지 않는다 · 잡의 마지막 VM 은 빼지 않는다 · OTP · 감사 |
| 백업 삭제 | 포탈 전용 잡의 그 VM(moref) 백업을 지운다(되돌릴 수 없음) — **잡에서 빼기에 성공해야** 지운다(마지막 VM·표기 차이로 확정 못 함·실패·모름이면 지우지 않음) | VM 이름 재입력 · OTP · 감사(실패·모름도 · 뺐는지·삭제 건수 항상) · 포탈 잡만 · 개체는 moref 로(이름 금지 · 없거나 둘 이상이면 지우지 않음) · 백업째 삭제는 그 백업에 이 VM 하나뿐일 때만 · 개체 삭제는 그 개체의 복원 지점이 전부 그 포탈 백업 안일 때만 |

같은 Veeam 서버로는 백업·복원·빼기·삭제가 **하나씩**이다(진행 중이면 409 — 관리 작업도 자리를 차지한다. 반증 F4: 동시에 빼면 한쪽 변경이 사라졌다).

포탈 백업 VM 목록(`veeam-portal-vms.json`)은 포탈이 **보낸 요청과 그 결과**다(VM 마다 한 줄 · 최근 복원 10건). Veeam 이 지금 가진 것은 관리 창이 Veeam 에 묻는다.

|---|---|---|
| 복원 지점 목록 `GET /api/v1/objectRestorePoints?nameFilter=` → `/api/v1/restorePoints` | 공식 v1 레퍼런스 목차(검색 결과) | **추정** — 개발 환경에서 레퍼런스가 열리지 않았다 |
| 새 VM 복원 `POST /api/v1/restore/vmRestore/vSphere`(type `Customized` · vmName · destinationHost · powerUp false) | Veeam 포럼 사용자 예시 | **추정** — 폴더·리소스 풀·데이터스토어를 지정하지 않는다(원래 호스트 기본값) — 서버가 요구하면 400 으로 거절되고 사유가 실행 기록에 남는다 |
| VM 단위 백업 삭제 `DELETE /api/v1/backupObjects/{id}` · (그 백업에 이 VM 하나뿐일 때) `DELETE /api/v1/backups/{id}` | — | **추정** — Veeam 직원 포럼 답변(날짜 미상)은 'REST 로 백업 삭제 불가' 라고 했다. 없으면 '잡에서 빼기까지만 했다 · 콘솔의 Delete from disk' 로 말한다 |

## 하지 않는 것

- 실행 중 백업 중지(Veeam 잡 중지는 잡 전체를 멈춘다 — Quick Backup 이면 원래 잡까지) · 원래 위치 복원(덮어쓰기) · Instant Recovery · 잡 스케줄 편집.

## 알려진 한계(2차 반증 검토에서 남긴 것)

- VM 을 백업한 B&R 서버를 **표시명**으로 찾는다(대조 결과가 서버 이름을 싣는다) — 등록부에 같은 표시명이 둘이면 첫 서버로 간다. 등록할 때 이름을 겹치지 말 것.
- vCenter 이름을 바꾸면 포탈 전용 잡 이름(접두 + 이름 + id 해시)이 바뀌어 새 잡이 생긴다 — 옛 잡은 Veeam 에 남는다(같은 VM 이 두 잡에).
- Detail 에서 넘기는 선택은 200대까지다(한 번 요청 상한과 같다).
- 엣지 워커가 다른 작업으로 바쁜 동안 인출 시한이 지나면 사유가 '엣지가 꺼졌거나 워커가 돌지 않음' 으로 적힌다 — 보내지 않은 것은 맞다.
