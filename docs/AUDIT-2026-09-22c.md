# v2.578 — 기간이 값을 바꾸는 이유를 화면이 말하게 (2026-09-22)

## 0. 이 감사의 출발점

v2.575·2.576·2.577 이 문서화된 축을 전수로 훑은 뒤, **릴리스 노트 자신이 적어 둔 미이행 약속**을
찾는 쪽으로 방향을 돌렸다. `server/src/release-notes.json:953`(v2.510.0)에 이런 문장이 있다:

> **남은 것(정직)**: … 기간별 결과 차이를 화면이 설명하지 않는 결함 4건(collectedSince 단정·기간
> 정규화 무표시·인과 설명 없음·화면별 해상도 불일치)은 **v2.511 로 분리**.

v2.511 은 SAN 조닝 릴리스였고, 그 뒤 **67개 릴리스 동안 이 넷은 처리되지 않았다**. 코드로 확인:
`web/src/views/trendMeta.js` 부재 · `toolsCapacity.js` 의 7일 폴백 존속 · `perfBatch.normDays` 의
30일 폴백 존속.

**교훈**: 릴리스 노트에 '다음 릴리스로 분리' 라고 적는 것은 추적 장치가 아니다. 노트 안에서 잊힌다.

## A. 확정 결함 4건 + 검증 중 발견한 자기 결함 1건

### D1 — `collectedSince` 를 '수집 시작' 이라 단정했다 (확정)

| 항목 | 내용 |
|---|---|
| 실제 값 | `max(수집 시작, 지금 − 보존일)` — `vmperfMeta().firstTs` 는 **prune 된 `samples` 의 MIN(ts)**(`metrics/vmperfDb.js:146` + `pruneVmperf:227`) |
| 보존 기본 | 90일 (`metrics/vmperfSettings.js:48`) |
| 화면이 하던 말 | "수집 시작: <날짜>. **더 긴 기간은 그만큼 시간이 지나야 채워집니다**"(`VCenterDetail.jsx`) · "**샘플러가 수집하는 시점부터** 쌓입니다"(`CapacityTools.jsx`) |
| 왜 거짓인가 | 90일 넘게 돌아간 포탈에서 120일·365일 구간은 **기다려도 영원히 채워지지 않는다**(보존이 90일이므로) |

**수정**: 서버가 `retentionDays` 를 함께 준다. 웹 `sinceNote()` 가 첫 표본이 보존 경계에 하루 이내로
붙어 있으면 `kind:'either'` 로 **두 원인을 함께** 말한다. 서버가 두 원인을 구분할 정보를 갖고 있지
않으므로(지워진 뒤에는 알 수 없다) **구분하지 않는 것이 정답**이다. `waiting` 플래그가 '기다리면
되는가' 를 들고 있고, 기다리라는 문구는 `waiting === true` 인 갈래에만 나온다(테스트가 고정).

### D2 — 입력 기간을 조용히 다른 값으로 바꿨다 (확정 · API 경로 한정)

| 라우트 | 프리셋 | 밖이면 |
|---|---|---|
| `GET /tools/rightsize` | 7·30·90·180·365 | **7** |
| `POST /vms/usage` (`perfBatch.normDays`) | 7·30·90·180·365 | **30** |

실측: `?days=14` → `{ requestedDays: 14, window.days: 7 }`.

⚠ **정직한 범위**: 현재 **화면 선택지는 프리셋뿐**이라 웹에서는 이 상황이 만들어지지 않는다.
주소로 직접 `days` 를 준 경우(또는 외부 호출)에만 성립한다. 그래도 응답이 요청값을 잃으면 소비자가
14일 결과라고 믿을 수 있으므로 `requestedDays` 를 실었다. ⚠ 캐시 키가 정규화된 `days` 이므로
`requestedDays` 는 **캐시 객체 밖**에 둔다(안에 넣으면 다른 요청의 값이 섞인다).

### D3 — 인과 설명이 없었다 (확정) + 구간 최대

**실측** — 목 서버에 90일치(시간당 1점, 매일 03시 스파이크)를 심어 실제로 조회:

| 기간 | 집계 단위 | 평균 사용률 | 평균선의 최고점 | 구간 최대의 최고점 |
|---|---|---|---|---|
| 7일 | 1시간 | 32.6% | **79%** | 79% |
| 30일 | 6시간 | 32.6% | **49%** | 79% |
| 60일 | 12시간 | 33.1% | **44%** | 79% |
| 365일 | 1일 | 33.1% | **44%** | 79% |

평균은 보존되고 **평균선의 최고점만 무너진다**. 이것이 사용자가 본 현상의 전부다.

**수정**: ① 각주가 그 인과를 적는다(`resolutionNote`) ② vCenter 추이 탭에 **구간 최대 토글**
(기본 꺼짐). 추가 쿼리 **0** — `vmperfHistory` 가 이미 버킷 최대(`MAX(mx)`)를 돌려주는데 `avg` 만
취하고 버리고 있었다.

### D3-b — 검증 중 발견한 **내 새 코드의 결함** (확정 · 같은 릴리스에서 수정)

구간 최대 **사용률**의 분모는 그 버킷의 **평균 할당**이다. 버킷 안에서 할당이 늘면 비율이 100% 를
넘는다 — 실측 **192%**(12시간 버킷 1개: 할당 729.7 GHz · 최대 1,400.5 GHz). 차트 y축이 `[0,100]`
이라 그대로 두면 **조용히 잘려 100% 에 붙은 선**이 되고, 그것은 '꽉 찼다' 는 적극적 거짓이다.

**수정**: 그런 구간은 `null` 로 비우고 개수(`maxPctUnstable`)를 화면이 호박색으로 밝힌다.
⚠ **클램프로 바꾸지 말 것** — 그것이 조용한 보정이다. 절대량(GHz·GB)은 언제나 옳으므로 그대로 둔다.

## D. 하지 않은 것 (정직 기록)

- **v2.510 계획 6번(vCenter 실측 설정 읽기)은 절반만 있다.** `vmseries/collect.js` 가
  `PerformanceManager.historicalInterval` 을 읽지만, `soapClient.js perfCounterMap()` 은 여전히
  `<level>` 을 파싱하지 않는다(`:314-319`). 그래서 `:891` 의 "전부 통계 레벨 1" 주석이 같은 파일
  `:941`·v2.481(`mem.active`·`mem.swapped` 는 레벨 2)과 어긋난 **낡은 주석**으로 남아 있다. 별건.
- **프리셋에 14일·60일을 추가하지 않았다.** 롤업 비용·표본 수 재검토가 필요한 별건이고, 이번
  변경의 목적은 '조용히 바꾸지 않는 것' 이지 '더 많은 기간을 지원하는 것' 이 아니다.
- **실제 vCenter 의 응답으로 확인하지 못했다.** 해상도 효과는 목 서버에 심은 90일 표본으로
  측정했다. 롤업 매핑과 계산은 실제 코드 경로를 그대로 탔지만, 현장 28개 vCenter 의 통계 레벨·
  보관 설정이 기본값과 다르면 차이의 **크기**는 달라질 수 있다(방향은 같다).
- **400px 상단 메뉴 가로 넘침 157px** — 기존 문제로 확정했으나 고치지 않았다. 앱 셸 전역이라
  v2.556·v2.572 의 폭 계약과 함께 별도 A/B 가 필요하다.
