### RSS 시계열 → 힙 스냅샷 → 확정 결함 2건(TUNE-B·C)

1. **관측**: `MOCK_SCALE=3` 목 서버(부하 없음)의 RSS 가 198 → 423MB(18분) 로 계속 올랐다. 힙 상한 160MB
   (`--max-old-space-size=160`)로 같은 서버를 띄우자 **9분 만에 heap OOM** 으로 죽었다 — GC 지연이 아니라
   **살아 있는 객체가 늘고 있다**는 증거.
2. **힙 스냅샷 2장(4.7분 간격) 비교**(`--heapsnapshot-signal` + 자체 분석기: 노드 id 가 스냅샷 간에 안정하므로
   '새로 생긴 노드' 의 retainer 경로를 3~4단계로 집계): 살아 있는 힙 156 → 219MB. 새 객체 54.7MB 의 대부분이
   `ipam/ledger.js` 의 **`_ipamCache > Map.table > Object.rows`** 아래였다.
3. **원인(TUNE-B)**: `_ipamCache`(rows)·`_sheetCache`(시트)는 키 첫 조각이 `snap.generatedAt`(세대)인데 '최근 32개'
   만 지켰다. `store.js:361` 이 **매 폴링(30초)마다** `buildIpamRows(snapshot)` 을 부르므로 세대마다 새 항목이
   추가되고, 지난 세대 항목은 **다시 히트할 수 없는데도** 32개가 찰 때까지 남았다(세대당 수 MB × 32).
4. **같은 유형(TUNE-C)**: `util/snapCache.js`(`memoJson` 이 쓰는 응답 캐시, 엔드포인트 42개)도 키가
   `${generatedAt}|url|scope` 이고 `MAX_PER_NAME=32` 다. v2.503 주석이 *"값은 스냅샷이 넘어가면 교체되므로
   메모리는 스냅샷 1세대분"* 이라 적었는데 **틀렸다** — 세대가 바뀌면 새 키가 추가될 뿐 옛 항목은 남는다.
   폴링 사용자 1명이면 16분 뒤 이름마다 32세대의 응답 객체가 상주한다.
5. **수정**: 두 모듈 모두 새 키를 넣을 때 **세대(첫 조각)가 다른 항목을 버린다**. 같은 세대의 여러 scope
   (다중 vCenter 동시 조회 — v2.503 이 32 로 올린 이유)는 그대로 남고 32 상한은 백스톱이다. snapCache 는 진행 중
   계산(promise)을 버리지 않는다(합류 중인 요청 보호). 첫 조각이 세대가 아닌 키(`anomalies|…`·`parts|…`)는
   한 세대로 취급되어 예전과 같다. 회귀는 `arch2580.test.js` ④⑤.
6. **수정 후 실측**: 같은 부하(대시보드 사용자 2명 · 폴링 라우트 9종 · 15초 · 8분, 요청 576건)로 A/B —
   · **부하 없음 4분**: 수정 전 heapUsed 49→~113MB(힙 상한 실험) / **ledger 수정 후 48→49MB(평탄)**.
   · **부하 8분, GC 직후 최저치**: A(ledger 만 수정 · snapCache 구판) 52 → 60 → **65MB(상승)** /
     B(둘 다 수정) 58 → 60 → **58MB(평탄)**. RSS 는 A 205→242MB, B 203→220MB.
   · 정직 기록: 이 목 부하에서 snapCache 몫은 7분에 약 +13MB 로 **작다**(값이 목 응답 객체라 작다). 운영에서는
     scope 수(법인 28)와 사용자 수만큼 곱해지지만 그 크기는 **측정하지 못했다** — 32세대 상한이 '곧 상한' 이라는
     구조적 사실만 확정한 것이다. ledger 쪽은 세대당 수 MB 라 목에서도 OOM 으로 드러났다.

## D. 고치지 않은 것과 이유
