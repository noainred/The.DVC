## 3. 정직하게 밝혀야 하는 것

**정정한 것**(이번 시안을 만드는 동안 내가 틀리게 적었다가 고친 것):

1. 기능 제안 때 ④ 를 ‘정방향 확인이 없다’ 고 했다 — 틀렸다. v2.993 에 물리서버 이름 → IP 방향의 정방향 확인이 있다(§2). 그래서 ④ 는 새 기능이 아니라 **반대 방향(역DNS 이름 → IP)을 더하고 지금 것과 합치는 일**이다.
2. ⑤ 충돌 보드 첫 판에 ‘호스트 · 물리 서버의 NIC MAC 은 수집에 없다’ 고 적었다 — 틀렸다. 물리 NIC MAC 과 iDRAC BMC MAC 은 수집된다. 없는 것은 **vmkernel NIC 의 MAC** 이다. 보드를 고쳤다(10:39 KST).
3. ⓪ 캡처 보드 첫 판에 카드 17 ‘신규 IP’ 를 ‘vCenter 수집이 처음 본 IP 기준’ 이라고 적었다 — 틀렸다. 스캔 이력의 `firstSeen` 기준이다. 보드를 고쳤다(10:44 KST).

**확인하지 못한 것**:

- 실제 L2 이웃이 있는 망에서 이웃 표 읽기를 시험한 적이 없다(이 컨테이너의 이웃은 게이트웨이 1개). ‘TCP 연결 · ping 을 한 IP 는 이웃 표에 MAC 이 남는다’ 는 리눅스 동작에 대한 일반 지식이고, 묶음마다 읽어야 얼마나 놓치지 않는지는 구현 때 실측해야 한다.
- 큰 대역(/22 이상)을 같은 서브넷에서 스캔하면 이웃 표 상한(1024)에 닿는다. 지금 스캔도 같은 조건이지만(MAC 을 읽지 않아 드러나지 않았을 뿐), 이때 MAC 을 얼마나 못 읽는지는 모른다 — 못 읽으면 ‘—’ 로 두는 규칙으로 막았다.
- 제조사 목록(IEEE 공개 등록부)의 **건수 · 파일 크기 · 재배포 조건**을 확인하지 않았다. 보드에는 ‘수만 건 · 크기는 구현 때 실측’ 이라고만 적었다. 재배포가 안 되면 추린 목록을 직접 작성하는 안으로 바꾼다.
- ESXi 의 vmk0 가 설치 때 물리 NIC 의 MAC 을 물려받는 경우가 많다는 것은 일반 지식이다(보장되지 않음 — 그래서 호스트 관리 IP 는 대조에서 뺐다).
- 가상 MAC 대역(VRRP `00:00:5E:00:01:xx` · HSRP `00:00:0C:07:AC:xx` 등)은 표준 · 벤더 문서의 값으로 알고 있는 것이며 이 환경의 장비로 확인한 것이 아니다.
- 충돌 의심 · MAC 변경의 **오탐률**은 모른다. vMotion · NIC 팀 구성 · 이중화 장비에서 어떻게 보이는지는 실환경 값이 필요하다 — 그래서 기본값을 보수적으로 잡고(연속 2회 · 충돌 의심만 켬) 릴리스를 나누자고 제안한다(§6-9).

**할 수 없는 것**(설계의 한계 — 보드 ⑤에 적음):

- 스캐너는 한 IP 에 대해 **한 번에 한 MAC 만** 본다. 같은 IP 에 두 장비가 번갈아 답하는 것을 한 스캔으로 확정하려면 원시 ARP 패킷(관리자 권한 · 전용 소켓)이 필요하다 — 넣지 않았다. 그래서 이름이 ‘충돌’ 이 아니라 **‘충돌 의심’** 이다.
- MAC 은 스캐너와 **같은 서브넷**에서만 보인다. 다른 서브넷의 IP 는 NetBIOS 가 답한 MAC 이 없으면 ‘—’ 이고 충돌 · MAC 변경 판정에서 빠진다(그 수를 ‘판정 못 함’ 으로 따로 센다).
- VM 의 IP 는 VMware Tools 가 보고한 값이다 — Tools 가 없거나 멈춘 VM 은 대조 대상이 아니다.
- DNS 답은 스캐너가 쓰는 DNS(운영체제 이름 풀이 — hosts 파일 포함)의 답이다. 분할 DNS 에서는 다른 곳의 답과 다를 수 있다.

## 4. 설계

### 4.1 변화 기록과 알림(①)

| 종류 | 판정 | 심각도 · 꼴 | 기본값(제안) |
|---|---|---|---|
| 충돌 의심 | vCenter 가 아는 VM 의 IP 에 그 VM 의 NIC MAC 이 아닌 MAC 이 응답(연속 2회) | 위험 · **상태형**(발생 · 쿨다운 재통지 · 해소) | 켬 |
| MAC 변경 | 같은 IP 의 MAC 이 지난 스캔과 다름(vCenter 가 모르는 IP) | 경고 · 사건형 | 끔 |
| 새 미등록 IP | vCenter 가 모르는 IP 가 처음 응답 — 대역 한 줄의 **첫 완료 스캔은 기준선** | 경고 · 사건형 · 묶음 상한 50 | 끔 |
| 예약 · 폐기 IP 사용 시작 | 관리상태(직접 지정 · 대역 정책)가 예약 · 폐기인 IP 가 응답 시작 | 경고 · 사건형 | 끔 |
| 호스트명 변경 | 같은 방식이 지난번과 다른 이름(v2.991 의 `renames`) | 경고 · 사건형 | 끔 |
| DNS 불일치 | 역DNS 이름의 정방향 주소가 그 IP 가 아님 | 기록만(알림 없음) | — |

- **기록은 전부, 알림은 고른 것만**: 끈 종류 · ‘알리지 않을 에이전트’ 의 변화도 ‘IP 변화’ 페이지에는 남는다(보드 ② · ③-8).
- **묶음**: 스캔 한 번 · 종류 하나에 알림 한 건(최대 10줄 + ‘외 N건’). 상한을 넘으면 요약 한 건(보드 ③-2).
- **보지 못한 것은 변화가 아니다**: 시한에 걸린 스캔은 비교하지 않는다. MAC ‘—’ 는 ‘변경 없음’ 이 아니다. 이전 버전 엣지는 알 수 있는 변화만 본다(보드 ③-4 · 5 · 6).
- **판정은 중앙에서 한 번**: 엣지는 결과만 올리고 ‘변화’ 를 보내지 않는다(엣지 판본이 달라도 같은 규칙 · 엣지가 보낸 값은 정제).
- **범위 계정**: 변화 기록 · 스캔 MAC 은 지금의 스캔 행과 같은 규칙으로 전 법인 계정에만 보인다. ‘IP 변화’ 페이지는 스캔 그룹의 다른 페이지처럼 관리자 전용.
- 사건형 넷은 지금의 `enqueueNotify` 로, 충돌 의심은 `evaluate` 의 규칙으로 넣는다(둘 다 지금 있는 경로 — 채널 · 쿨다운 · 실패 처리를 새로 만들지 않는다).

### 4.2 MAC · 제조사(②)

- 스캔 자식 프로세스가 묶음마다 이웃 표 파일을 읽어 응답한 IP 의 MAC 을 붙인다(새 패킷 없음 · 명령 실행 없음). 출처를 함께 싣는다 — `arp`(직접 봄) 또는 `netbios`(상대가 말함). 둘 다 있으면 `arp` 를 표시하고 NetBIOS 값은 상세 창에 따로.
- 제조사는 MAC 앞 3바이트를 포탈에 실린 목록과 대조한다. 임의 지정 MAC(둘째 16진수가 2 · 6 · A · E)은 제조사를 추정하지 않고 ‘임의 지정 MAC’, 목록에 없으면 ‘제조사 미상’.
- 가상 NIC 대역의 MAC 인데 vCenter 가 모르는 IP 면 ‘미등록 가상 NIC’ 칩으로 모은다(단정하지 않는다 — 다른 가상화 · 등록되지 않은 ESXi 일 수 있음).
- 화면: 대장 목록에 ‘제조사 · MAC’ 열(호스트명 다음) · 요약 줄 ‘MAC n / N · 제조사 확인 · 임의 지정’ · 칩 둘 · IP 상세 창의 MAC 묶음(현재 MAC · 출처 · MAC 이력 · 같은 MAC 의 다른 IP · ‘MAC 변경 알림 제외’) · 에이전트 표의 ‘MAC’ 칸(읽은 수 · 못 읽은 이유).
- 값이 없거나 믿기 어려운 경우 9종은 보드 ⑥.

### 4.3 충돌 감지(③)

판정 순서(보드 ⑤): ① 완료된 스캔 + MAC 을 읽음 → ② 가상 MAC · 여러 IP 에 답하는 MAC 은 뺌 → ③ VM 의 IP 인데 스캔 MAC 이 그 VM 의 NIC MAC 목록에 없으면 충돌 의심 → ④ vCenter 가 모르는 IP 는 지난 MAC 과 비교(처음 읽은 MAC 은 기준선) → ⑤ 충돌 의심은 연속 2회에서 알림.
해소: 다음 완료 스캔에서 그 VM 의 MAC 이 응답하거나 vCenter 에서 그 VM 의 IP 가 바뀌면 해소. 스캔이 그 IP 를 보지 못한 동안은 ‘모름’(해소도 유지도 아님 · 재통지 없음).
화면: 추천 탭의 새 카드 ‘충돌 의심 · MAC 변경’(판정 · IP · 대장이 아는 것 · 스캔이 본 것 · 처음 본 때 · 에이전트) + ‘판정 못 함 N’ 을 따로.

### 4.4 DNS 정합성(④)

- 역DNS 가 답한 이름을 정방향으로 다시 묻는다 — 결과 넷: **일치**(주소 목록에 그 IP 가 있음) · **다른 IP** · **정방향 없음** · **확인 못 함**(시한 · 예산 — 일치에도 불일치에도 넣지 않음).
- v2.993 의 묻는 함수 · 시한 · 동시 수 · 차단기를 그대로 쓴다. 순서는 물리서버 이름 먼저, 남은 예산으로 역DNS 이름. 결과는 하루 동안 다시 쓰고 오래된 것부터 묻는다. 묻는 곳은 스캔을 돌린 쪽(법인 엣지 → 법인 DNS).
- 화면: 어긋난 것만 배지(‘DNS 다른 IP’ · ‘정방향 없음’) · 칩 ‘DNS 불일치’ · 요약 줄 · IP 상세 창 역DNS 줄 아래의 정방향 결과 · 추천 카드 16 을 ‘DNS 정합성’ 으로(레코드 초안은 아래에 그대로) · CSV `dns_forward` 열.
- v2.993 의 `nameVia` 배지와 겹치지 않게 둘을 한 자리에서 정한다(구현 때 조합 표를 테스트로 고정).

### 4.5 데이터 계약(늘어나는 것 — 이름은 구현 때 확정)

| 어디 | 늘어나는 것 | 정제 |
|---|---|---|
| 엣지 → 중앙 결과의 IP 한 건 | `macSrc`(`arp` · `netbios`) · 정방향 결과(상태 + 주소 1개) | 열거값 · IPv4 꼴 · 길이 상한 — `cleanAliveHost` 화이트리스트에 등록 |
| 엣지 → 중앙 보고(`nameStats` 옆) | MAC 통계(읽은 수 · 대상 수 · 못 읽은 이유 코드) | 수는 `numOrNull` · 이유는 열거값 |
| 저장 결과 · 이력 | MAC 이력(값 · 출처 · 처음 · 마지막 — 상한 있는 목록) · 정방향 결과와 확인 시각 | 저장본 로드 때도 같은 정제 |
| 새 파일 | 변화 기록(고리 버퍼 · 보존 일수 = 스캔 결과 보존과 같게) · 대역별 기준선 표시 | 원자적 쓰기 · 한 번에 |
| 알림 설정 | IP 관리 규칙 5개의 켬/끔 · 묶음 상한 · 알리지 않을 에이전트 | 지금의 `saveAlertConfig` 정제에 추가 |
| 관리상태 | ‘MAC 변경 알림 제외’ 표시 | 불리언 |

## 6. 컨펌 질문(기본값은 제안)

1. **알림 기본값** — 기본: ‘충돌 의심’ 만 켬, 나머지 넷은 끔(기록은 전부 남김). 대안: 전부 켬 / 전부 끔.
2. **‘IP 변화’ 의 자리** — 기본: IP관리 서브메뉴 ‘스캔’ 그룹의 새 페이지(관리자 전용). 대안: 대장 목록 안의 탭.
3. **대장 목록의 ‘제조사 · MAC’ 열** — 기본: 호스트명 다음에 열 추가. 대안: 상세 창에만 두고 목록은 칩 · 배지만.
4. **제조사 목록의 범위** — 기본: IEEE 공개 등록부 전체로 만든 파일을 릴리스에 싣는다(크기는 구현 때 실측해 보고 · 재배포 조건 확인 뒤). 대안: 데이터센터 장비 중심으로 추린 목록(작지만 ‘제조사 미상’ 이 늘어남).
5. **충돌 의심을 알리는 시점** — 기본: 연속 2회 스캔(설정값). 대안: 1회(빠르지만 vMotion · IP 교체 직후의 엇갈림도 알림).
6. **iDRAC(BMC) 주소 대조** — 기본: 이번에 넣지 않음(대장이 iDRAC 주소를 출처로 갖고 있지 않아 등록부와 잇는 일이 따로 듦). 대안: 포함.
7. **DNS 정합성의 범위** — 기본: 역DNS 이름의 정방향 확인만. 대안: NetBIOS · mDNS 이름이 DNS 에 등록돼 있는지도(도메인 접미사 설정이 필요).
8. **DNS 불일치 알림** — 기본: 기록만. 대안: 알림 규칙으로도.
9. **릴리스 나누기** — 기본: 세 번(가: MAC · 제조사 수집과 표시 → 나: 변화 기록 · 알림 · 충돌 감지 → 다: DNS 정합성). 엣지 수신 계약이 두 번 바뀌고, 충돌 · MAC 변경은 실환경 값을 보고 조정할 여지를 두려는 것. 대안: 한 번에.
10. **검증 수준** — 기본: 표준 + 변이 검증 1회(엣지 수신 정제 · 변화 감지 · 이웃 표 파서) + Chromium 1440/400. 대안: 전체 검증(반증 에이전트 포함).

범위 밖(요청하면 추가): Windows 에서 도는 스캐너의 MAC 읽기(`arp -a` 파서) · 원시 ARP 로 두 MAC 동시 확인 · 스위치 MAC 표와의 대조(CVP) · SMB/TLS 인증서 이름.
