작성 2026-11-12 (main v2.914.0 기준) · 상태 **시안 — 사용자 컨펌 대기(구현 전)** · 시안 캔버스: https://claude.ai/artifact/T9Bc9DpEyZF1nHTW7k6Zi7
(아트보드 5장 — 이 폴더의 `*.dc.html` + `bmf.css` 가 같은 내용의 레퍼런스. 법인 · 서버 이름 · 서비스 태그 · 주소 · 대수는 **전부 그림용 가상값**이고

## 1. 요구(사용자 2026-11-12)

> "물리서버 서비스별 분류하기 작업을 할꺼야, 가상화 서버는 vcenter 가 자동으로 분류하는데, 물리서버는 구조적으로 분리할 수가 없어, 물리서버를 폴더 형식으로 관리하고 싶어 …
> vcenter 의 클러스터 처럼 전체 서버를 폴더 형식에 서버를 등록하는 기능인데, idrac 에서 인식된 서버들을 이곳 폴더에 추가하는 기능 … 검색 기능으로 특정 문자가 포함된 서버를
> 검색해서 한번에 등록하는 기능 … 물리서버는 중앙에서 엣지의 서버들도 등록하는 기능 필요해 · 시안 만들어서 보여줘"

## 2. 지금 코드에서 확인한 것(설계의 근거)

| 사실 | 위치 |
|---|---|
| 물리서버 목록의 단일 출처는 **통합 서버 인벤토리 분류**다 — iDRAC 등록부 · OME · 수집 서버(pull) · 엣지 push 를 모아 ‘가상화 호스트 / 베어메탈’ 로 나눈다. 행 = `{serverId, fleetId, name, model, serviceTag, source, vcenterId …}` | `insights/fleetInventory.js classifyFleet` · `getFleetInventory` |
| 엣지는 **베어메탈 목록만** 중앙에 올린다(`setEdgeFleet(agent, baremetal, …)`) — TTL · 못 읽음 보류(`UNREADABLE_HOLD_MS`) · 부분 목록 표지가 이미 있다 | `central/fleet.js` |
| 베어메탈의 법인(vCenter) 귀속은 등록부 → 수동 지정(`fleet-assign.json`) → DataCenter 단일 vCenter 순. 귀속 없는 서버가 따로 세어진다 | `idrac/serverByCorp.js` 머리말 · `insights/fleetAssign.js` |
| **서비스 인벤토리(v2.887)** 가 이미 VM + 베어메탈을 서비스 단위로 묶는다. 베어메탈이 서비스에 붙는 길은 **고정(한 대씩) · 스캔 엔트리 라벨 · 이름 규칙** 셋이고, VM 의 ‘vCenter 폴더 규칙’ 에 해당하는 것이 베어메탈에는 없다. 그 화면의 ‘폴더’ 는 **서비스를 담는 폴더**이지 서버를 담는 폴더가 아니다 | `servicemap/resolve.js` · `servicemap/CLAUDE.md` |
| 베어메탈 안정 키 = `st:<서비스태그>`(없으면 `fl:<fleetId sha1 16자>`) · 키 등급 승계(`aliasKeys`) · 유령/보류 판정이 구현돼 있다 | `servicemap/CLAUDE.md` ‘키’ · ‘고정’ |
| 범위 규칙: 조회는 `scopedVcenterIds` 교집합 · 쓰기는 ‘조회 밖 404 → 쓰기 밖 403’(`corpWriteAccess`) · 법인 미지정 구성원과 전 법인 동작은 전체 범위 관리자 · 범위 계정 판본에는 베어메탈 서비스 태그를 싣지 않는다 | `servicemap/CLAUDE.md` ‘범위’ |

## 4. 설계 결정(시안에 그린 것 — 컨펌 대상)

1. **새 도구 ‘물리서버 폴더’**(도구 키 가칭 `bm-folders`). 통합 서버 인벤토리(분류 · 법인 귀속)와 서비스 인벤토리(서비스 · 규칙) 사이에 놓인다.
2. **트리는 법인 › 폴더(여러 단계)** — vCenter › 클러스터와 같은 꼴이고, 법인 단위 범위 · 쓰기 권한이 그대로 선다. 법인을 넘는 보기는 ‘폴더 이름별(전 법인)’ 읽기 전용 합산으로 준다.
3. **한 서버는 한 폴더에만**(호스트 ↔ 클러스터와 같은 규칙) — 대수 합이 항상 맞고(전체 = 등록 + 미분류 + 법인 미지정) ‘추가’ 가 아니라 ‘이동’ 이다.
4. **대상은 베어메탈이 기본**, ‘ESXi 호스트 포함’ 은 찾기에서 고르는 선택(ESXi 호스트는 이미 vCenter 클러스터로 나뉜다).
5. **검색 일괄 등록**: 정규식이 아니라 ‘포함’(대소문자 무시 · 길이 상한 · 선형 — 정규식 규약) · 쉼표로 여러 글자 · 제외 글자 · 찾는 곳(이름 · 호스트명 · 서비스 태그 · 모델 · iDRAC 주소는 관리자만).
   전 법인으로 찾으면 서버는 **자기 법인의 같은 이름 폴더**로 들어가고 없는 법인에는 폴더를 만든다. 이미 다른 폴더에 있는 서버는 기본으로 건드리지 않는다. 등록 전에 법인별 증감을 미리 보인다.
6. **자동 규칙(선택)**: 검색 조건을 ‘이름에 포함 → 폴더’ 규칙으로 저장하면 새로 인식되는 서버도 들어간다. 손으로 넣은 등록이 규칙보다 우선.
7. **엣지 서버도 중앙에서 등록**: 등록 정보는 **중앙에만** 저장한다(`CONFIG_DIR/bm-folders.json` 가칭 — 비밀 없음 · 원자 쓰기 · rev). 엣지 push 계약은 바꾸지 않는다(엣지가 올린 베어메탈 목록의 키로 조인).
   엣지 보고가 만료되면 등록은 두고 흐리게 · 측정값 ‘—’ · 없어진 서버 판정은 보류.
8. **서비스 인벤토리 연결(2단계)**: ‘물리서버 폴더 규칙’(폴더 경로 → 서비스)을 VM 의 vCenter 폴더 규칙과 같은 순위에 둔다. 판정 순서가 바뀌므로 옮겨 가는 구성원을 검토 큐에 먼저 보이고 릴리스 노트에 고지한다.

## 6. 정직 기록 — 확인하지 못한 것

- 시안 렌더 확인은 캔버스 런타임이 아니라 **정적 판본**(`<x-dc>` 를 `<div>` 로 바꾼 것)을 로컬 Chromium 으로 본 것이다(이 컨테이너에서 런타임의 외부 스크립트 · 웹 글꼴을 받지 못함).
  1440 · 400 에서 넘침 · 잘림 0 을 측정하고 스크린샷 5장을 판독했다. 실제 캔버스에서는 글꼴(Inter · Noto Sans KR) 폭이 달라 줄바꿈이 다를 수 있다.
- 대수 · 사용률 · 전력은 가상값이다. 실제 미분류 규모 · 엣지별 서버 수는 구현 때 실측한다.
- 수집 서버(pull) 경로 서버의 키가 엣지 push 와 같은 등급으로 오는지는 구현 때 대조한다(서비스 인벤토리의 ‘스캔 엔트리 id 는 세 경로’ 와 같은 문제일 수 있다 — 추정).
