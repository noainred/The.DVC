## 5. 정직하게 밝혀야 하는 것

- 값은 **목(mock, 가상) 서버의 한 시점**(2026-11-18 11:09:08 KST · VM 2,242 · 법인 11곳)을 `/api/vms` 로 한 번 받아 법인별로 집계한 것이다 — 지어낸 수는 없다. 실제 환경(28 vCenter · 약 5,850 VM)의 값이 아니다.
- 목 서버 값은 법인마다 거의 같다(평균 CPU 50 ~ 53% · 조치 필요 20 ~ 22%). 그래서 **법인 지도의 색이 전부 같은 단계**로 보인다 — 눈금을 절대값으로 둔 탓이며, 실제 값에서는 법인마다 갈린다. 색 차이를 보이려고 눈금을 좁히지 않았다(작은 차이를 부풀리는 것은 틀린 그림이다).
- 위 숫자 3장 중 Hypervisor(호스트 186 · 확인 대상 35)는 같은 목 서버의 10:52 값이다(VM 값과 받은 시각이 다르다).
- **캔버스에서 띄워 눌러 보지 않았다**(Design 캔버스는 요청이 있을 때만 검증). 확인한 것은 보드 스크립트의 동작 논리다 — node 에서 실행해 합계(2,242 / 1,966 / 473 · vCPU 11,957 · 메모리 42.2 TB · 디스크 719.3 TB) · 지도 배치(열 폭 합 100% · 열마다 높이 합 100%) · 누름(칸 · 칩 · 지역 · 색/크기 기준 · 찾기 · 보기 줄) · 템플릿 값 누락 0 을 확인했다. **배치가 겹치거나 넘치는지는 재생으로 봐야 안다.** 템플릿 문법은 사용자가 이미 눌러 본 ⑦ 과 같은 것만 썼다.
- **‘유휴 후보’ 는 지금 포탈에 없는 새 판정**이다(구동 · CPU 10% 미만 · 메모리 30% 미만 — 기준은 제안값). 순간값으로 세면 잠깐 한가한 VM 도 잡히므로 구현은 기간 평균이어야 한다 — 기간 값이 어디까지 있는지는 구현 전에 확인해야 한다(미확인).
- 하드웨어 버전 옆 괄호(ESXi 세대)는 VMware 의 버전 대응(vmx-10 = 5.5 · 13 = 6.5 · 15 = 6.7 U2 · 17 = 7.0 · 19 = 7.0 U2)을 내가 아는 대로 적은 것이다 — 구현 때 문서로 다시 확인한다.
- 추가분(디스크 패널 · 과할당)의 값도 같은 목 서버에서 받았다 — 게스트 파티션 사용률은 11:23:00 에 한 번(`/api/tools/guest-partition`), Optimization 은 11:26 에 법인마다 한 번씩(`/api/tools/waste?vcenterId=…`). **VM 값(11:09)과 받은 시각이 달라** 수가 서로 조금 어긋난다(예: 구동 VM 1,966 대 1,800 — 목 서버 값이 주기마다 흔들린다). 합계는 도구의 전체 응답과 대조했다(초과 VM 226 · 파티션 272 · 위험 2 · 곧 가득 14 / CPU 후보 176 · 메모리 후보 367 · 꺼짐 304 · 스냅샷 347 · Tools 미실행 95).
- 보내 주신 Optimization 캡처에는 실제 VM · 호스트 이름이 보인다 — **시안과 이 문서에는 옮기지 않았다**(목 서버의 가상 이름만 쓴다).
- 과할당 요약에는 ‘7일 사용률 추이’(작은 선 그래프)를 넣지 않았다 — 목 서버에 쌓인 추이가 없어 그릴 값이 없다. 도구에는 그대로 있다.
- ‘곧 가득 찰 파티션’ 의 일수는 도구가 계산한 값(`etaDays`)을 반올림한 것이다 — 지난 7일의 증가가 이어진다는 가정이라 예상일 뿐이다.
- 400px 보드는 만들지 않았다(이번 범위 밖). 좁은 화면에서는 요약 2열 · 패널 1열 · 법인 지도는 지역을 세로로 쌓는 구성을 생각하고 있다 — 필요하면 보드로 그린다.
- 넣지 않은 것: **VM 수 추이(30일)** — 포탈에 ‘VM 수량 추이’ 도구는 있지만 목 서버에 쌓인 추이가 없어 선을 그리지 않았다(지어낼 수 없다). OS 지원 종료 표시 · 백업 보호율 · 태그/폴더별 분포도 같은 이유 또는 범위 문제로 뺐다(§6 ⑤).

## 7. 구현 메모(컨펌 뒤 · Opus)

- **집계는 서버에서 한 번에**: 화면이 VM 5,850대를 받아 세면 안 된다. 새 응답(예: `/vms/insight`)이 법인별 줄(이 보드의 `rows()` 와 같은 모양 — 수 · 합 · 분포 배열)을 준다. 화면은 고른 법인의 줄을 더하기만 한다(복수 선택에 서버 왕복이 없다).
  상시 폴링 경로이므로 `memoJson` + `extraKey: scopeKey(...)`(+ 역할) · 큰 집계는 조각 + 시간 기준 양보(`createYielder`) — `docs/rules/perf-db.md`. 범위 계정은 조회 범위 안의 법인 줄만 받는다(교집합 먼저).
- **못 읽은 값은 0 이 아니다**: 사용률 미수집 VM 은 평균 · 히스토그램 · 유휴 판정에서 빼고 따로 센다(`util/numOrNull.js`). 엣지 위임 법인의 값이 늦으면 그 법인 줄에 ‘오래됨’ 을 표시하고 합에 섞지 않는다.
- 판정은 하나: 과부하 · Tools · 스냅샷은 지금 신호 판정(`signals`)을 그대로 쓴다. ‘유휴 후보’ 는 새 판정이라 서버 한 곳에 두고 테스트로 고정한다.
- OS 계열(Windows / Linux / 기타)은 `guestOS` 문자열에서 정한다 — 모르는 이름은 ‘기타’ 로 세고 0 으로 숨기지 않는다. OS 종류가 8개를 넘으면 뒤쪽을 ‘그 밖’ 으로 접는다.
- 화면: 보기 키 `insight` 를 `HUB_VIEWS` 맨 앞에(주소 `#/vms/insight` · 지금 `#/vms` 는 새 기본으로) — 저장된 주소 `#/vms/list` 는 그대로 열린다. 법인 지도의 칸 · 지역 줄 · 분포 칸을 누르면 바로가기 선택 또는 ‘목록’ 의 조건(지금 `facets`)으로 이어진다.
- 표가 아닌 목록 · 차트지만 ‘지금 볼 VM’ 은 `STable`(제목 클릭 정렬) · 문구에 백틱 금지 · 그리드 자식 `min-width:0` · Chromium 1440 · 400.
- **디스크 패널 · 과할당은 새 계산을 만들지 않는다** — `guestpart/report.js overview`(응답의 `kpi` · `vcenters[]` · `rows[]`)와 `/tools/waste`(`overAllocated` · `poweredOff` · `snapshots` · `thinReclaim` · `noTools` · `byVcenter[]`)를 그대로 쓴다. 판정을 화면에서 다시 하지 않는다(판정 코어는 하나).
  법인별 합이 필요한 값 중 응답에 없는 것 — 초과 파티션의 구간별 수 · OS 별 수 · ‘곧 가득’ 의 법인별 수(게스트 파티션) / CPU · 메모리의 법인별 할당 · 사용 · 미사용(Optimization 의 `byVcenter` 에는 후보 수만 있다) — 은 서버 응답에 더한다(화면이 줄 300개를 세지 않게 · `LIST_LIMIT` 에 잘린 목록으로 세면 틀린다).
- 권한이 다르다: VM 목록은 `invVms`, 두 도구는 `requirePerm('tools')`. 도구 권한이 없는 계정에 요약이 새지 않게 — 패널 · 칸을 숨기거나(§6 ⑪) 403 을 권한 안내로. 범위 계정은 두 API 가 이미 조회 범위로 거른다(그대로 쓴다).
- 무거운 API 다: 게스트 파티션 사용률은 화면에서 60초 시한으로 부른다(`GuestPartTool.jsx`) — **15초 폴링에 얹지 않는다**. 마운트 1회 + ‘다시 받기’ 버튼, 늦게 온 이전 응답은 버린다. 분석 보기의 다른 패널이 이 응답을 기다리지 않게 따로 그린다(받는 중 · 못 받음 · 오래됨을 패널 안에 표시).
- 복수 선택: 두 API 는 지금 `vcenterId` 한 곳만 받는다 — `docs/design/vm-menu/` 의 `vcenterIds` 를 여기에도 적용하거나, 법인별 줄을 받아 화면에서 더한다(이 시안의 방식).
- 링크: ‘모두 보기’ 는 `#/tools/guest-partition` · `#/tools/waste` 로 — 고른 법인이 한 곳이면 그 범위를 들고 간다.
- 이 시안은 `docs/design/vm-menu/` 의 복수 선택(서버 `vcenterIds`)이 먼저 있어야 위 숫자 3장 · 다른 탭과 범위가 맞는다 — 같이 구현하거나 그 뒤에 구현한다.
