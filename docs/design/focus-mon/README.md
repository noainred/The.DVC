## 1. 요구 (사용자 요청 2026-11-11)

> 특수기능에 "집중 모니터링" 이라는 메뉴를 추가하고 중앙/엣지에 연결된 서버의 성능 지표를 모니터링 해서 실시간으로 볼 수 있는 기능
> 1. 복수로 최대 20개의 서버의 정보를 동시에 수집 · 2. cpu, memory, network, disk 를 실시간으로 화면에 · 차트로 비교 ·
> 3. network 은 본딩된 인터페이스, 개별 인터페이스의 사용율을 각각 · 4. disk 는 전체 디스크, 개별 디스크, 파티션별 read/write/latency,wait 을 1개 서버 ~ 최대 20개 서버에서 차트로 비교 ·
> 5. 단수/복수 서버에서 top 30개 프로세스의 cpu 사용율 분석 — "구현방법과 시안 만들어서 보여줘"

## 3. 정직하게 밝혀야 하는 것

1. **RHEL 7.8 실장비에서 확인하지 않았다.** 아래 명령 · 필드 구성(커널 3.10.0-1127 · `/proc/diskstats` 14칸 · OpenSSH 7.4 · procps-ng 3.3.10 · gawk 4.0 · util-linux 2.23)은 문서와 기억 기준이다.
   이 환경에는 RHEL 7.8 서버가 없다. 구현 1단계에서 **실서버 1대의 수집 원문**을 받아 테스트 픽스처로 고정해야 한다(§12). 그 전의 파서는 ‘맞을 것’ 이지 ‘맞다’ 가 아니다.
2. **‘실시간’ 은 수 초 늦다.** 중앙 연결 서버 약 2~4초, 엣지 연결 서버 약 4~8초(주기 2초 + 엣지 → 중앙 전송 2초 + 고지연 법인 왕복 0.8초 이상 + 화면 조회 2초 — **설계 추정값**, 구현 뒤 실측으로 바꾼다).
3. **프로세스 CPU 는 5초 차이값이다.** 그 사이에 생겼다 사라진 프로세스는 보이지 않고, 처음 본 프로세스는 다음 표본부터 값이 나온다(top 과 같은 한계).
4. **지연(await)은 요청이 없으면 값이 없다.** 그 구간에 읽기(쓰기)가 0건이면 ‘—’ 이고 0 ms 가 아니다. 차트는 선을 끊고, 20대 × 시간 띠는 ‘값 없음’ 칸으로 둔다.
5. **링크 속도를 못 읽으면 사용률(%)을 내지 않는다**(가상 인터페이스 · 일부 드라이버는 -1). 수신 · 송신량만 보여 준다. team 드라이버 본딩은 구성원은 알 수 있으나 모드는 못 읽을 수 있다(추정 — 미확인).
6. **대상 서버에 주는 부하를 재지 않았다.** SSH 세션 1개 + 2초마다 `/proc` 파일 5개 읽기 + 5초마다 awk 1회다. 가볍다고 **추정**하지만 프로세스가 수천 개인 서버에서는 awk 비용이 커질 수 있어, 한 번 도는 데 걸린 시간을 재서 표본 주기를 스스로 늦춘다(§5.4).
7. **`/proc` 이 `hidepid` 로 마운트된 서버**에서는 전용 계정이 다른 사용자의 프로세스를 못 본다. `/proc/mounts` 로 감지해 ‘이 계정에 보이는 프로세스만’ 이라고 화면에 말한다.
8. **명령줄 가림은 완전하지 않다.** `password` · `token` · `secret` · `key` 뒤의 값만 잡는다(자유 문자열). 그래서 명령줄은 관리자 판본에만 싣는다.
9. **기록은 DB 에 남지만 비정상 종료 때는 아직 묶이지 않은 최대 약 1분을 잃는다.** 실시간 화면용 60분 버퍼(메모리)는 재시작하면 비고, 과거 구간은 DB 에서 다시 읽는다.
   ‘30일 뒤로’ 는 **그 시간에 수집 중이었을 때만** 값이 있다 — 켰던 시간만 기록이 있고 나머지는 빈다(§9-2 ‘꼭 정해야 하는 것’).
10. **옛 판 엣지는 이 기능을 모른다.** 그 엣지의 서버는 ‘업그레이드 필요’ 로 보이고 수집하지 않는다(엣지 자동 업그레이드 v2.859 가 있어 보통 곧 풀린다).
11. 시안의 지연 · 처리량 · 프로세스 값은 전부 가상이다. Oracle · java 프로세스 이름은 화면 모양을 보이려는 예시다.
12. **iostat 과 일부러 다르게 보이는 곳이 두 군데 있다**(사용자가 보낸 출력에서 확인한 경우다).
    ① 그 구간에 끝난 요청이 0건이면 iostat 은 `await` 를 0.00 으로 찍는다 — 화면은 ‘—’ 로 둔다(0 ms 로 읽히지 않게).
    ② 끝난 요청은 0건인데 **걸린 요청이 있고 사용률이 100%** 인 장치(보낸 출력의 sdd: r/s 0 · w/s 0 · avgqu-sz 2.00 · %util 100.00)는 가장 나쁜 상태인데 iostat 줄은 조용하다 — 화면은 ‘응답 없음’ 배지와 안내 줄을 붙인다.
13. **지연 눈금을 고정하면 안 된다.** 보낸 출력에는 `w_await` 3,076 ms · `r_await` 2,271 ms 가 있다. 처음 시안의 0~50 ms 고정 눈금은 이런 값을 천장에 붙여 버린다 → 세로축은 값에 맞춰 잡고 로그 눈금을 고를 수 있게 했다(§7).

## 4. 구조 — 데이터가 흐르는 길

```
[대상 서버 RHEL 7.8]            [담당 노드: 중앙 또는 엣지]                 [중앙 포탈]                 [브라우저]
 sshd ── SSH 세션 1개(키) ──▶ 수집기: 고정 스크립트를 한 번 실행           수신 · 정제 · 메모리 링버퍼      2초마다 증분 조회
 bash 반복문이 2초마다         → 구획(##STAT ##MEM ##NET ##DISK ##PROC)      (서버당 60분)                 (탭이 가려지면 멈춤)
 /proc · /sys 를 그대로 출력     을 받아 **노드에서** 비율 · 지연 · 상위 30 계산
                               ├ 중앙이 맡은 서버 ─────────────────────▶ 같은 프로세스 안에서 바로 적재
                               └ 엣지가 맡은 서버 ── 2초마다 묶어 POST ──▶ /api/central/focus-mon/sync
                                                  ◀─ 응답에 ‘지금 수집할 대상 목록 · 유효 시각’
```

- **백업 · 수집은 법인 로컬, 현황은 중앙**(CLAUDE.md 운영 환경 2026-11-01)을 그대로 따른다. 엣지가 자기 망의 서버에 붙고, 원문(`/proc` 덤프)은 법인 밖으로 나가지 않는다. 중앙에는 계산된 숫자만 온다.
- 서버 수만큼 WAN 을 왕복하지 않는다. 엣지 1곳 = 2초에 요청 1건(서버 20대 분을 한 묶음으로).
- **끝나는 시각이 반드시 있다**: 수집 시한(기본 15분 · 연장) · 보는 화면이 없으면 60초 뒤 정지 · 엣지는 중앙과 30초 끊기면 스스로 정지(받는 쪽 TTL 보다 짧게).
  예외는 관리자가 일부러 켠 ‘계속 수집’ 하나다(§9-2 · §10 ⑯) — 그때도 엣지의 30초 규칙은 그대로이고, 다시 이어지면 스스로 재개한다.
- 중앙은 받은 값을 1분 단위로 묶어 `focusmon.db` 에 남긴다(30일). 실시간 화면은 메모리를, 과거 구간은 DB 를 읽는다.

## 5. 수집 — RHEL 7.8 에서 무엇을 읽고 어떻게 계산하나

### 5.1 접속

- 대상은 **IPv4 주소 · 포트(기본 22) · 계정 · 담당 노드**로 등록한다. 비밀번호 · 개인키는 받지도 저장하지도 않는다.
- 인증은 **담당 노드의 키**다. 노드마다 키가 다르다(중앙 1개 · 엣지마다 1개) — 개인키가 망을 건너지 않는다. 키 종류는 ECDSA P-256(기존 `isidu/sshKey.js` 와 같은 이유: ssh2 의 ed25519 생성기는 자기 파서가 거부하는 키를 가끔 만든다). OpenSSH 7.4 는 이 키를 받는다(문서 기준).
- 이미 쓰는 키가 있으면 그 개인키를 노드의 `<CONFIG_DIR>/ssh/` 에 복사해 둘 수 있다(`id_ed25519` · `id_ecdsa` · `id_rsa` — 기존 모듈의 후보 순서 그대로). 화면 · API 로 경로를 받지는 않는다.
- 대상 서버 계정은 **권한 없는 전용 계정**이면 된다(예 `dvcmon`). 읽는 것이 `/proc` · `/sys` 뿐이라 root · sudo 가 필요 없다. `authorized_keys` 에는 `from="<노드 주소>",restrict` 를 붙이도록 화면이 명령을 만들어 준다(시안 ⑤).
- 서버 한 대에 **SSH 세션은 하나**이고 수집이 끝날 때까지 열어 둔다. 표본마다 다시 로그인하지 않는다(대상 서버 `/var/log/secure` 에 2초마다 로그인 기록이 쌓이지 않게 · 핸드셰이크 비용 제거).
- 키 거부(인증 실패)는 **자동으로 다시 시도하지 않는다**(`util/authGuard.js` 규약). 사람이 ‘다시 연결’ 을 눌러야 한다. 호스트키 거부는 인증 실패와 다른 코드로 구분한다(기존 규약).

### 5.2 대상 서버에서 도는 스크립트(고정 문자열 — 사용자 입력이 들어가지 않는다)

주기 값만 정수 1 · 2 · 5 · 10 중 하나로 치환한다. 그 밖의 어떤 문자열(이름 · 경로 · 인터페이스)도 명령에 넣지 않는다.

```sh
LC_ALL=C; export LC_ALL; I=2; P=5
echo '##HELLO 1'; uname -srm; cat /etc/redhat-release 2>/dev/null; getconf CLK_TCK; nproc; grep -c hidepid /proc/mounts
n=0
while :; do
  echo "##T $(cut -d' ' -f1 /proc/uptime) $(date +%s)"       # Δt 는 uptime 차이(시계 보정에 흔들리지 않게)
  echo '##STAT'; grep '^cpu' /proc/stat                       # 전체 + 코어별
  echo '##LOAD'; cat /proc/loadavg
  echo '##MEM';  cat /proc/meminfo
  echo '##NET';  cat /proc/net/dev
  echo '##DISK'; cat /proc/diskstats
  if [ $((n % 15)) -eq 0 ]; then                              # 30초마다: 구성(자주 안 바뀐다)
    echo '##NETTOPO'                                          # 인터페이스별: 속도 · 상태 · master · 본딩 모드 · 구성원 · active
    for d in /sys/class/net/*; do … speed operstate master bonding/mode bonding/slaves bonding/active_slave …; done
    echo '##BLKTOPO'; lsblk -P -b -o NAME,KNAME,PKNAME,TYPE,SIZE,MOUNTPOINT 2>/dev/null
  fi
  if [ $(( (n * I) % P )) -eq 0 ]; then                       # 5초마다: 프로세스별 누적 CPU 시간
    echo '##PROC'; awk '{ …마지막 ")" 뒤에서 utime stime starttime rss 를 뽑아 pid 와 함께 한 줄… }' /proc/[0-9]*/stat 2>/dev/null
  fi
  echo '##END'; n=$((n+1)); sleep $I
done
```

- 파일을 만들지 않는다 · 설치하는 것이 없다(sysstat · iostat 이 없어도 된다) · 세션이 끊기면 반복문도 끝난다.
- `top` 출력을 읽지 않는다 — 계정의 `~/.toprc` · 로캘에 따라 열이 바뀐다. `/proc/<pid>/stat` 는 형식이 고정이다.
- 상위 30개가 정해진 뒤에만 그 PID 들의 사용자 · 스레드 수 · 메모리 · 실행 시간 · 명령줄을 같은 SSH 연결의 두 번째 명령(`ps -ww -o … -p <숫자 목록>`)으로 가져온다. 새로 들어온 PID 만 묻고 `(pid, starttime)` 으로 기억한다.

### 5.3 계산식 — 판정 코어는 `focusmon/rates.js` 하나(순수 함수 · 서버와 엣지가 같은 파일)

| 항목 | 식(두 표본의 차이 Δ, Δt 는 대상 서버 uptime 차이) | 못 구하면 |
|---|---|---|
| CPU 사용률 | `1 − (Δidle + Δiowait) / Δ합계` · 구성 = 사용자 · 시스템 · I/O 대기 · steal · irq 를 각각 `Δ항목 / Δ합계` | 첫 표본 · 카운터 역행 → null |
| 메모리 사용률 | `(MemTotal − MemAvailable) / MemTotal` · 버퍼 · 캐시 · 스왑 · Dirty · Slab 은 순간값 | MemAvailable 없으면 기존 폴백(`parseMemInfo`)과 그 사실 표시 |
| 인터페이스 수신 · 송신 | `Δ바이트 × 8 / Δt`(bps) · 오류 · 드롭은 Δ개수 | null |
| 인터페이스 사용률 | `max(수신, 송신) / 링크 속도` | 속도 미상 → 사용률 null(처리량만) |
| 본딩 사용률 | 본딩 인터페이스 자신의 카운터 ÷ 본딩 속도. 속도 = 802.3ad · balance 계열은 **링크가 올라온 구성원 속도의 합**, active-backup 은 **사용 중인 구성원 하나** | 구성원 속도 중 하나라도 미상 → null |
| 디스크 IOPS | `Δ읽기 완료 수 / Δt` · `Δ쓰기 완료 수 / Δt` | null |
| 디스크 처리량 | `Δ섹터 × 512 / Δt`(MB/s) | null |
| **읽기 · 쓰기 지연**(latency) | `Δ읽기에 걸린 ms / Δ읽기 완료 수` · 쓰기도 같음 — iostat 의 `r_await` · `w_await` | Δ완료 수 = 0 → **null**(0 아님) |
| **대기열**(wait) | `Δ가중 대기 ms / Δt / 1000` — iostat 의 `avgqu-sz` | null |
| 디스크 사용률 | `Δio_ticks / Δt / 10`(상한 100) — iostat 의 `%util` | null |
| 병합 | `Δ병합된 읽기 요청 수 / Δt` · 쓰기도 같음 — iostat 의 `rrqm/s` · `wrqm/s` | null. dm 장치는 항상 0(병합은 아래 물리 디스크에서 일어난다) |
| 평균 요청 크기 | `Δ(읽기 섹터 + 쓰기 섹터) / Δ(읽기 + 쓰기 완료 수)` — iostat 의 `avgrq-sz`(섹터 = 512바이트) | Δ완료 수 = 0 → null |
| 합친 지연 | `Δ(읽기 ms + 쓰기 ms) / Δ(읽기 + 쓰기 완료 수)` — iostat 의 `await` | Δ완료 수 = 0 → **null**(iostat 은 0.00) |
| 서비스 시간 | `Δio_ticks / Δ(읽기 + 쓰기 완료 수)` — iostat 의 `svctm`. sysstat 설명서가 ‘더 믿지 말라’ 고 밝힌 값이라 **참고용**으로만 둔다 | Δ완료 수 = 0 → null |
| 걸린 요청 | `/proc/diskstats` 12번째 칸(지금 진행 중인 요청 수 · 순간값) | 완료 0건 + 걸린 요청 1건 이상 + 사용률 100% → 상태 ‘응답 없음’ |
| 전체 디스크 | **물리 디스크만** 더한다(파티션 · LVM · 멀티패스 dm 은 같은 입출력을 다시 보는 것). 지연은 요청 수 가중 평균, 사용률은 최고값 | 물리 디스크 0개 → null |
| 프로세스 CPU | `Δ(utime + stime) / CLK_TCK / Δt × 100`(1코어 = 100%) · 서버 대비 = `÷ 코어 수` | 첫 표본 · PID 재사용(starttime 다름) → null |

- 쓰는 칸(`/proc/diskstats` · 커널 3.10 은 14칸): 4 읽기 완료 수 · 5 읽기 병합 · 6 읽기 섹터 · 7 읽기 ms · 8 쓰기 완료 수 · 9 쓰기 병합 · 10 쓰기 섹터 · 11 쓰기 ms · 12 진행 중 · 13 io_ticks · 14 가중 대기 ms.
  스크립트는 이 파일을 통째로 내보내므로(§5.2) 13개 열을 더해도 대상 서버에서 도는 명령은 바뀌지 않는다.
- **사용자가 보낸 iostat 출력으로 식을 대조했다**(2026-11-11 22:16 · `node` 계산): `svctm` sdj 1000 ÷ 52 = 19.23(화면 19.23) · sdd 1000 ÷ 3 = 333.33(화면 333.33) ·
  `await` sdd (2360 × 1 + 0 × 2) ÷ 3 = 786.67(화면 786.67) · sde (2271 × 1 + 0.73 × 470) ÷ 471 = 5.55(화면 5.55) ·
  `avgrq-sz` sdj 7.85 × 2048 ÷ 52 = 309.17(화면 309.08) · sde 6.33 × 2048 ÷ 471 = 27.52(화면 27.51) — 뒤 두 건의 차이는 화면의 MB/s 가 소수 둘째 자리로 반올림된 값이라서다.
  ⚠ 대조한 것은 **식**이다. 그 서버가 RHEL 7.8 인지는 확인하지 않았고, `/proc/diskstats` 원문을 본 것도 아니다(§3-1 은 그대로 남는다).
- ‘wait’ 은 두 가지로 읽힐 수 있어 **둘 다** 둔다: 디스크 대기열(위 표)과 CPU 의 I/O 대기 비율(CPU 구성의 한 칸). §10 ⑥.
- 수치 판정은 전부 `util/numOrNull.js` 로 한다(`Number('') === 0` 함정). 부분만 읽힌 합(예: 디스크 4개 중 3개만)은 ‘전체’ 로 내지 않고 읽은 개수를 함께 싣는다.
- 장비 출력 파싱에 앵커 없는 무제한 반복 정규식을 쓰지 않는다. 줄 길이를 먼저 자른다(4KB) · 구획당 줄 수 상한(디스크 512 · 인터페이스 128 · 프로세스 20,000).

### 5.4 주기와 보호

- 지표 주기 1 · 2 · 5 · 10초(기본 2초) · 프로세스 5초(지표 주기가 더 길면 그 값) · 구성(본딩 · 마운트) 30초.
- 한 바퀴가 주기의 절반보다 오래 걸린 서버는 그 서버만 프로세스 표본을 10초 → 20초로 늦추고 화면에 그 사실을 적는다.
- 노드당 SSH 스트림 상한(기본 40) · 포탈 전체 동시 수집 3건 · 한 수집에 서버 20대. 같은 서버를 두 수집이 고르면 **세션 하나를 함께 쓴다**(참조 수).
- 표본이 주기의 3배 넘게 안 오면 ‘지연’ 으로 표시하고 마지막 값을 흐리게 둔다. 0 으로 내리지 않는다.

## 6. 서버 모듈

### 6.1 키 — `util/sshKeyStore.js`(새 파일 · `isidu/sshKey.js` 의 일반화)

- 집중 모니터링은 `name: 'focusmon_key'` · env `FOCUSMON_SSH_KEY`. 개인키는 어떤 응답 · push · 백업에도 싣지 않는다(기존 불변조건 그대로).
- 엣지는 등록된 대상이 생겼다는 것을 중앙 응답으로 알았을 때 키를 만들고, 다음 요청에 공개키 · 지문을 올린다. 중앙은 노드별 공개키를 작은 파일(`focusmon-keys.json` — 비밀 아님)에 기억해 엣지가 꺼져 있어도 화면에 보인다.

### 6.3 엣지 — `agent/focusMonWorker.js` + `central/focusMonEdge.js`

- **깨우기**: 수집 시작 · 대상 변경 때 중앙이 해당 엣지의 수집 URL 로 `POST /api/collector/focus-mon/wake` 1회(`X-Collector-Token`). 닿지 않는 엣지(중계 경로)는 엣지의 **30초 폴백 조회**로 시작한다 — 시작이 최대 30초 늦는다고 화면이 말한다.
- **동기화**: 수집 중인 엣지는 2초마다 `POST /api/central/focus-mon/sync`(`X-Central-Token` · gzip). 요청 = 그동안 모인 표본 묶음 + 서버별 상태 + 공개키 · 지문 + 버전. 응답 = 지금 수집할 대상 목록(`id · host · port · username`) · 주기 · `validUntil`.
  - 큐가 아니라 **원하는 상태**라서 어느 쪽이 재시작해도 다음 요청에서 맞춰진다(claim → ack 가 필요 없다).
  - 요청이 겹치지 않는다(앞 요청이 끝나야 다음). 회선이 느리면 표본이 한 묶음에 여러 개 실리고, 묶음이 800KB 를 넘기면 오래된 표본부터 버리고 ‘빠진 구간’ 표지를 싣는다.
  - 엣지는 `validUntil`(30초)이 지나도록 성공한 동기화가 없으면 모든 수집기를 닫는다.
- **중앙 정제**(엣지가 보낸 것은 믿지 않는다): 아는 필드만 · 객체만 · 배열 상한(서버 20 · 인터페이스 32 · 블록 128 · 프로세스 30) · 문자열 길이 상한 · 수치는 `numOrNull` · 이름은 인증된 agent · 표본 시각은 수신 시각으로 자르고 원본은 따로. 그 엣지가 맡지 않은 대상 id 는 버린다(다른 법인 서버의 값을 덮어쓰지 못하게).
- 엣지 워커는 0건이어도 상태를 남긴다(`_last` · 콘솔 · `edgelog/spec.js` 등재).

### 시간 띠 — 구간 단위와 이전 · 다음(추가 요청 22:19)

- **구간**은 1 · 5 · 10 · 30분 넷이다. 이전 · 다음 단추는 **고른 구간만큼** 한 칸 움직인다(5분이면 ‘◀ 이전 5분’). 슬라이더는 오른쪽 끝이 최신이고 한 눈금이 한 칸이다.
- 띠 하나가 **그 화면의 모든 차트**를 함께 옮긴다(차트마다 따로 두지 않는다). 개요의 카드 숫자는 그 구간 끝의 값이 된다.
- 갈 수 있는 범위는 **DB 에 남은 30일**이다(결정 2026-11-11). 슬라이더는 최근 24시간(날짜를 고르면 그 날 하루)을 움직인다 — 1분 1,439칸 · 5분 287칸 · 10분 143칸 · 30분 47칸. 그보다 먼 날은 **‘날짜로 이동’** 으로 간다. 이전 · 다음 단추는 날짜 경계를 넘어 계속 간다.
- 슬라이더 아래 얇은 띠가 **기록이 있는 시간**을 칠한다(수집하지 않은 시간 · 엣지가 끊긴 시간은 빈다). 기록이 없는 구간에 서면 ‘이 구간에는 기록이 없습니다’ 와 앞 · 뒤 기록으로 가는 단추를 보인다(시안 ⑥). 0 으로 그리지 않는다.
- **과거 구간은 갱신하지 않는다**(보던 곳이 흘러가지 않게). 그동안에도 수집은 계속되고, ‘최신’ 을 누르면 그 사이 값이 채워진 최근 구간으로 돌아온다. 띠 아래 글이 ‘최근 구간’ 인지 ‘과거 구간 · 뒤로 몇 칸째’ 인지 말한다.
- 슬라이더는 **놓을 때만** 조회한다(기존 `WindowScroll` 규칙). 고른 구간은 브라우저가 기억한다.
- 한 구간의 표본이 많으면(30분 = 2초 표본 900개) 화면은 최대 150칸으로 줄여 그린다. 평균만 쓰면 순간 급등이 사라지므로 **칸 평균과 칸 최고값**을 함께 받아 선과 얇은 띠로 그린다.
- 프로세스 탭에도 같은 띠가 있다(프로세스 목록도 DB 에 남는다 — 결정 2026-11-11 · §9-2). ‘구간 끝 순간’ 과 ‘구간 평균’ 가운데 고른다.

### iostat 비교 — 고른 서버의 iostat 을 나란히(추가 요청 22:37 · 아트보드 ②-2)

- **고른 서버의 장치 줄을 한 표에 놓는다.** 열은 iostat -x -m 의 13개 그대로이고 모든 서버가 같은 열 자리를 쓴다. 서버마다 터미널을 띄워 따로 볼 때와 달리 **같은 표본 시각**으로 맞춘다(서버끼리 2초 안쪽으로 어긋나므로 가장 가까운 표본).
- **배치 두 가지**: ‘서버별로 묶기’(서버 머리줄 아래 전체 디스크 줄 + 장치 줄) · ‘한 표로 섞어 정렬’(묶음을 풀고 고른 열로 모든 서버의 장치를 한 줄로 세운다 — 어느 서버의 어느 디스크가 가장 느린지). 열 제목을 누르면 정렬(`STable`).
- **칸 짙기**: 칸 바탕이 짙을수록 그 열에서 큰 값이다(모든 고른 서버를 통틀어 · 한 색 농담 · 로그 비율 — 3,000 ms 같은 값 하나가 나머지를 지우지 않게). 전체 디스크 줄은 칠하지 않는다.
- **차트에 올리기**: 줄 앞 네모를 누르면 그 장치가 아래 추이 차트에 올라간다(최대 4줄 · 검증한 4색 · 표의 네모와 같은 색). 차트의 값은 지금 정렬한 열이다(열 제목을 누르면 같이 바뀐다). 눈금 선형 | 로그.
- **장치 범위**: 물리 디스크만(기본) | 파티션 · 볼륨 포함 · 찾기(장치 이름 · 마운트 — 예 `sdb` · `/oradata`) · 조용한 장치 숨기기(읽기 · 쓰기가 모두 0 인 줄 — 숨긴 개수를 서버 머리줄에 적는다).
- **값의 시점**: 구간 끝 순간 | 구간 평균. 구간 평균은 표본 값의 단순 평균이 아니라 **요청 수로 가중**해 다시 계산한다(지연 = 걸린 시간의 합 ÷ 끝난 요청 수의 합 — 표본마다 `r/s × Δt` 로 요청 수를 되살린다).
- 시간 띠는 다른 화면과 같다 — 과거 구간이면 DB 에서 읽고, 서버 고르기에는 그때 기록이 있는 서버가 나온다.
- 서버 20대 × 장치 17개면 340줄이다. 조용한 장치 숨기기가 기본이고, 그래도 많으면 표 안에서 세로로 민다(가로는 상자 안에서만).
- API: `GET /data?targets=&view=iostat&scope=phys|all&at=end|avg&win=&end=` — 서버마다 장치 줄 × 13개 값 + 구성(이름 · 종류 · 마운트) + 상태(지연 위험 · 응답 없음). 차트는 `view=compare:disk:<열>:dev:<서버>/<장치>,…`.

### 20대를 한 차트에 어떻게 보이나(요구 2 · 4)

- 색 20개로 선 20개를 그리지 않는다 — 색각 이상에서 구분이 안 되고(검증 스크립트 기준) 범례를 읽을 수 없다. 세 가지를 같이 둔다:
  1. **작은 차트 여러 개**(개요): 서버마다 같은 세로축(0~100%)의 작은 추이. 높낮이가 곧 비교다.
  2. **강조**(비교): 고정한 서버 최대 4대만 색 선 + 끝 이름표, 나머지는 회색 선. 색은 서버를 따라간다(정렬 · 필터가 바뀌어도 그대로).
  3. **순위 막대 + 농담 띠**(비교): 지금 값은 막대 20개, 시간 흐름은 서버 20줄 × 시간 칸의 한 색 농담.
- 단위가 다른 두 값(MB/s 와 ms)은 한 차트에 두 축으로 겹치지 않는다(§서버 상세는 차트 2개).
- 수신 · 읽기 = 파랑 `#3987e5`, 송신 · 쓰기 = 주황 `#d95926`. 포탈의 기존 ↓ 청록 · ↑ 호박(전송 속도 화면)은 검증 스크립트의 어두운 바탕 밝기 범위를 벗어나 쓰지 않았다 — 맞추기를 원하면 바꿀 수 있다(§10 ⑪).
- 상태(주의 · 위험)는 색만으로 말하지 않고 배지 낱말을 붙인다. 못 읽은 값은 ‘—’ 이고 단위를 붙이지 않는다.

### 구현 때 지킬 화면 규약(이 저장소 규칙)

- 표는 `components/STable.jsx`(제목 클릭 정렬 · null 은 항상 뒤) · 문구 모듈 `focusMonText.js` 하나 · 차트 좌표는 순수 모듈 `focusMonChart.js`(테스트) · 문구에 백틱 금지 · `text-transform: uppercase` 금지.
- 시안의 주기 · 대수 · 임계 숫자는 화면에 박지 않고 `GET /` 응답 값으로 그린다.
- 도구 키 `focus-mon` 은 정하면 바꾸지 않는다. 별칭(`aka`): 실시간 모니터링 · 서버 성능 · top · iostat · 본딩 · 프로세스.

## 8. 보안 · 권한

- **adminOnly + fullScopeOnly**: 전 법인 서버의 주소 · 프로세스 · 명령줄이 나온다. 대상이 vCenter 귀속이 아니라 범위 계정에 나눌 축이 없다(전송 속도 · 통신 점검과 같은 기준). 범위 계정은 403.
- 개인키는 노드를 떠나지 않는다 · 등록부에 비밀이 없다 · 요청 본문으로 주소 · 계정을 받아 **즉석 접속하지 않는다**(대상은 등록부에서만).
- 대상 서버에서 실행되는 문자열은 고정 스크립트 + 정수 주기 + 숫자 PID 목록뿐이다(명령 주입 여지 없음 — 테스트로 고정).
- 호스트키는 기존 장비 신뢰 관문을 그대로 탄다. 승인 저장소는 노드마다 따로다(엣지 서버는 그 엣지에서 승인).
- 엣지 수신은 §6.3 정제 + 그 엣지가 맡은 대상만. 엣지 이름은 토큰으로 인증된 이름이다.
- 이 기능은 **읽기만** 한다. 프로세스 종료 · 우선순위 변경 · 원격 명령 실행 같은 조작은 넣지 않는다.

## 9-2. DB 저장 · 30일 보관 검토 (요청 2026-11-11 22:27)

> "뒤로 갈 수 있는 길이 30일, 데이터를 DB 에 저장하면 가능한지 검토해줘" · "DB 에 저장해줘"(프로세스 목록)

**결론: 가능하다.** 다만 2초 표본을 한 줄씩 넣는 방식으로는 안 되고, **서버 1대 · 1분 = 한 줄(압축 묶음)** 로 넣어야 한다.

### 왜 한 줄씩은 안 되나

- 이 포탈의 SQLite 는 동기 API 다(`node:sqlite` — `docs/rules/perf-db.md` ‘대량 SQLite 쓰기 오프로딩’). 넣는 동안 이벤트 루프가 선다.
- 장치 17개인 서버 1대가 2초마다 장치 줄 17개를 넣으면 하루 73만 줄, 20대 30일이면 **약 4.4억 줄**이다. 인덱스 · 정리 · 조회가 모두 감당이 안 된다.
- 1분 묶음으로 넣으면 20대 30일이 **86만 줄**(지표) + 86만 줄(프로세스)이다.

### 저장 모양

- 파일 `focusmon.db`(다른 시계열 DB 와 같은 폴더 · WAL · `util/sqliteOpen.js` 규칙). 포탈 백업 번들에는 넣지 않는다(백업은 .json · .env 만 — 기존 불변조건).
- `fm_metric(target, minute, res, n, schema, data BLOB)` — 기본 키 `(target, minute)` · `minute` 단독 인덱스(정리용). `data` 는 그 1분의 모든 시리즈를 열 방향으로 놓고, 소수 둘째 자리 정수로 바꿔 앞 값과의 차이를 가변 길이 정수로 적은 뒤 deflate 한 것이다.
- `fm_proc(target, minute, data BLOB)` — 그 1분의 프로세스 표본(신원표 = PID · 시작 시각 · 사용자 · **가림을 거친** 명령줄, 표본마다 번호 · CPU · 메모리)을 gzip 한 것.
- `fm_schema(id, target, hash, json)` — 시리즈 이름표(인터페이스 · 장치 구성). 구성이 바뀔 때만 한 줄 늘고, 묶음은 그 번호를 가리킨다.
- `fm_run(id, started, ended, by, mode, interval, targets)` — 수집 기록(누가 · 언제 · 어느 서버 · 방식). 시간 띠의 ‘기록이 있는 시간’ 과 감사에 쓴다.
- 최근 60분은 지금처럼 메모리에도 있다. 실시간 화면은 DB 를 읽지 않고, 과거 구간만 DB 에서 읽는다.

### 꼭 정해야 하는 것 — ‘30일 뒤로’ 는 그 시간에 수집하고 있었어야 볼 수 있다

지금 설계의 수집은 사람이 켰을 때만 돌고 15분 뒤 스스로 멈춘다. 이대로 DB 에 남기면 30일 안에서도 **켰던 시간에만** 기록이 있다.
장애가 시작된 때로 돌아가 보려면 그때도 수집 중이어야 하므로, 시한 없는 **‘계속 수집’** 방식을 함께 둔다(§10 ⑯ — 기본은 ‘잠깐 보기’).

- 계속 수집은 최대 20대(포탈 전체 합) · 관리자가 끌 때까지 · 보는 화면이 없으면 기록 주기를 10초로 낮춘다(대상 서버 · 회선 · DB 부담을 약 1/5 로).
- 그 대가: 대상 서버에 SSH 세션이 상시 열려 있고, 엣지 → 중앙 전송이 상시 흐른다(10초마다 서버 20대 묶음 20~60 KB — 압축 전 · 추정).
- 포탈 · 엣지가 재시작하면 계속 수집은 스스로 다시 시작한다(끄기 전까지 유지되는 설정이다 — 등록부에 남긴다).
- 키 거부로 멈춘 서버는 계속 수집이어도 자동으로 다시 붙지 않는다(§5.1).

### 쓰기 · 읽기 · 정리 규칙 (`docs/rules/perf-db.md` 대로)

- **쓰기**: 분이 바뀌면 그 분의 묶음을 만들어 대기열에 넣고, 10초 틱에 **한 트랜잭션**으로 넣는다(한 번에 최대 40줄 — 측정 0.4 ms). 그래서 워커로 넘기지 않는다. 쓰기 시간을 계측해 두고 운영에서 p99 가 50 ms 를 넘으면 `ipam/writeWorker.js` 방식으로 옮긴다.
- 엣지가 늦게 보낸 표본은 그 분의 묶음을 다시 만들어 덮는다(`INSERT OR REPLACE`). 5분보다 늦은 표본은 버리고 그 수를 센다.
- **종료 때 flush** — 남은 분을 넣고 닫는다. 비정상 종료면 아직 묶이지 않은 **최대 약 1분**을 잃는다(§3-9).
- **읽기**: 과거 구간은 `(target, minute)` 범위 조회 뒤 풀기. 서버 20대 × 30분은 600묶음이라 **시간 기준 양보**(`createYielder`)를 끼우고, 풀어 둔 묶음은 작은 LRU 에 둔다. 요청 하나가 읽는 묶음 수에 상한(서버 20 × 30분)을 둔다.
- **정리**: 보관 기간(기본 30일 · 설정 1~90일)이 지난 줄을 500줄 조각으로 지운다 — 스로틀 `(++tick % N) === 0`(기동 첫 틱 금지) · `minute` 단독 인덱스 · `util/chunkedPrune.js`.
- **용량 상한**(기본 20 GB · 설정): 넘으면 보관 기간 안이라도 가장 오래된 것부터 지우고 화면에 그 사실을 적는다. SQLite 파일은 지워도 바로 줄지 않는다(빈 자리를 다시 쓴다).
- **디스크 여유 보호**: 포탈 서버의 여유 공간이 기준 아래면 **기록만** 멈춘다(수집 · 화면은 계속). 시안 ⑥ 의 띠.
- 못 읽은 값은 묶음 안에서도 null 표식이다(0 으로 적지 않는다). 기록이 없는 분은 줄이 없다 — 화면은 ‘기록 없음’ 으로 비운다.

### 엣지가 끊긴 동안

엣지는 보내지 못한 표본을 메모리에 최대 10분 두었다가 이어지면 보낸다(계속 수집일 때만). 그보다 길게 끊기면 그 구간은 비고, 시간 띠에 빈 칸으로 보인다. 엣지에는 DB 를 두지 않는다(§10 ⑳).

- ⑧ · ⑮ **명령줄은 모으지 않는다 — 프로세스 이름(comm)만.** 시안 기본은 ‘전체(가림)’ 였으나 이 저장소에 이미 같은 규칙이 있다
  (`docs/rules/security-api.md` 8b Top-N — ‘comm 만 · 인자 · 환경 · 열린 파일 없음’). 가림은 아는 형태만 지우므로 인자 속 비밀을 전부 막지 못한다.
  명령줄이 필요하면 사용자 결정으로 따로 연다(그때 가림 · 관리자 판본 · DB 보관 범위를 다시 정한다).
- ⑫ **‘수집 원문 내려받기’ 는 넣지 않았다.** 연결 시험은 키 로그인 · 커널 · 배포판(RHEL 판) 확인까지다. RHEL 7.8 실서버 원문은 아직 없다 —
  파서 픽스처는 이 환경의 컨테이너 리눅스(6.18) 원문뿐이다(`server/test/fixtures/focusmon/`). 실서버 1대의 원문을 받으면 픽스처로 고정해야 한다.
- ① 키는 노드가 만든 전용 키(`focusmon_key`)가 기본이고, 이미 쓰는 키 파일은 env `FOCUSMON_SSH_KEY` 경로로만 쓴다(화면에서 파일을 올리는 경로는 없다).
- 메뉴 이름 ‘집중 모니터링’ 은 기존 ‘베어메탈 사용률’ 안의 집중 모니터링(bmusage focus — iDRAC · 베어메탈 등록부 기반)과 이름이 같다. 요청대로 이 이름을 쓰고,
  도구 설명에 ‘다른 화면’ 이라고 적었다. 두 기능을 합치지 않았다(대상 · 접속 방식 · 기록이 다르다).
- DB 묶음은 시안의 열 이름 표(`fm_schema`) 대신 묶음 안에 열 이름을 함께 싣는다(서버마다 디스크 · 인터페이스 이름이 달라 표가 커진다 — 묶음 1분 평균 약 8KB 측정값에 포함).

2. **지표 · 값** — 디스크는 iostat 13개 열 가운데 하나, 네트워크는 수신 · 송신 · 사용률 · 오류 · 드롭. 값은 **평균 | 최고(1분)**.
3. **장치(인터페이스) × 24시간 표** — 칸마다 숫자 + 바탕 진하기(그 표의 가장 큰 값 대비 로그 비율 — 기존 `focusMonChart.js cellShade` 와 같은 방식). 오른쪽에 기간 평균 · 가장 높은 시.
   수집하지 않은 시간은 ‘·’ · 일부만 수집한 시간은 점선 밑줄 · 끝난 요청이 없으면 ‘—’. 본딩 구성원은 들여 쓰고, 값이 0 뿐인(링크 끊김) 인터페이스는 한 줄로 접는다.
4. **고른 장치의 시간별 표** — 장치 이름을 누르면 아래에 그 장치의 24줄(시간 · 수집한 분 · 요약 8열 또는 iostat 13열 · 가장 느린 1분). 네트워크는 수신/송신 평균 · 최고 · 사용률 · 오류 · 드롭.
   위에는 막대 차트(시간 평균 막대 + 그 시간의 최고 금). 시(時)를 누르면 표의 줄 · 차트의 띠가 같이 표시된다.
5. **1분 단위 화면으로 이동** — 시를 고른 뒤 누르면 위쪽 시간 띠가 그 시각으로 옮겨져 그때의 차트 · 실시간 표 · 프로세스를 본다(시간 평균 → 원본으로 내려가는 길).

### 15.3 계산 (새 판정을 만들지 않는다)

- 시간 평균은 **지금의 ‘구간 평균’ 과 같은 계산**을 1시간 창에 적용한다(`server/src/focusmon/query.js averageSample` — 횟수 · 처리량은 시간 평균, 지연은 요청 수 가중, `rates.js` 코어).
  판정 코어를 복제하지 않는다 — 시간 창만 다르게 넘긴다.
- ‘최고(1분)’ = 그 시간 안의 1분 묶음(`fm_metric` 한 행 = 1분) 60개 각각의 평균 가운데 가장 큰 값. 표본 하나의 순간값이 아니라 1분 평균이라 튀는 표본 하나에 덜 흔들린다.
- 네트워크 오류 · 드롭은 평균이 아니라 **그 시간의 합**(누적 카운터의 차이)이다.
- 시 경계는 포탈 시각(`util/dayKey.js DAY_OFFSET_MIN`) — 30분 단위 시간대(+05:30)에서도 분 묶음을 그대로 나누므로 경계 칸 문제가 없다(v2.978 의 kWh 경계 결함과 다른 구조).

### 15.4 정직하게 밝힐 것

1. **수집한 시간만 있다.** ‘잠깐 보기’ 는 켠 동안만, ‘계속 수집’ 은 끌 때까지 기록한다. 수집하지 않은 시간은 빈 칸이고 0 이 아니다. 하루 종일 보려면 그 서버를 ‘계속 수집’ 으로 둬야 한다.
2. **일부만 수집한 시간**(60분 미만)은 평균을 내되 표시를 달고 덮은 분 수를 적는다 — 22분의 평균을 1시간의 평균처럼 보이게 하지 않는다. 진행 중인 시간도 같다.
3. **시간 평균은 튀는 값을 가린다.** 3초짜리 지연이 5분만 있었으면 시간 평균은 수백 ms 로 내려간다. 그래서 ‘최고(1분)’ 을 같이 둔다.
4. **비용을 재지 않았다(추정).** 하루 = 서버 한 대의 분 묶음 최대 1,440개(장치가 많으면 묶음이 크다)를 풀어야 한다. 그래서
   ① 끝난 시간은 바뀌지 않으므로 (대상 · 시) 단위로 결과를 캐시하고 ② 푸는 동안 시간 기준으로 양보하고(`createYielder`) ③ 화면은 열 때 한 번 + ‘새로고침’ 으로만 읽는다(상시 폴링 없음 — 루트 CLAUDE.md ‘무거운 API’ 규칙).
   첫 조회가 몇 초 걸릴 수 있다 — 구현 때 디스크 300개 서버로 측정해 상한(한 번에 하루)을 정한다.
5. 시안의 수치 · 서버는 가상이다(결정적 난수). 시안 스크립트는 node 로 돌려 값이 나오는 것만 확인했고, **캔버스에 그려진 모습은 확인하지 않았다**(디자인 캔버스 작업 규칙 — 요청 없이는 렌더링 검증을 하지 않는다).
