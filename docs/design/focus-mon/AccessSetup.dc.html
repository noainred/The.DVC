정직하게 밝힐 것

  • 지금까지 집중 모니터링은 ‘접속은 키만 · 공개키는 사람이 넣는다 · 포탈은 대상 서버에 계정을 만들지 않는다’ 였습니다. 자동 준비는 그 규칙의 예외입니다 — 준비할 때 한 번, 준비에 쓸 계정으로만, 포탈이 만든 준비 파일만 root 로 돕니다. v3.17.0 의 ‘설치할 때 한 번’ 에 이어 root 로 도는 경우가 둘이 됩니다.
  • 엣지 OS 의 root 키를 포탈이 알아서 쓰지는 못합니다. 엣지에서 사람이 root 로 SSH 가 되는 것과 포탈이 그 키를 쓸 수 있는 것은 다릅니다 — 엣지마다 한 번, 그 엣지 포탈의 SSH 공용 접속에 키를 등록해야 합니다(소유자 등급 + OTP). 그 키가 root 접속용이라는 점은 등록하는 분이 판단합니다.
  • sshd 설정은 읽기만 합니다. AllowUsers · AllowGroups · DenyUsers 로 막혀 있거나 공개키 로그인이 꺼져 있으면 포탈이 고치지 않고 멈춥니다(서버 담당자의 정책이므로).
  • 새로 만든 계정은 비밀번호가 잠긴 상태입니다. 서버의 비밀번호 만료 정책(예: 90일)이 그 계정에도 걸리면 몇 달 뒤 키 로그인이 거부될 수 있습니다(추정 — PAM 계정 검사. 이 환경에서 재현해 보지 않았습니다). 그래서 포탈이 만든 계정에는 만료를 끄는 것을 기본값으로 제안합니다(확인 창에서 바꿀 수 있음 · 이미 있던 계정은 건드리지 않음).
  • sshd 가 PAM 을 쓰지 않도록(UsePAM no) 설정된 서버에서는 비밀번호가 잠긴 계정의 키 로그인이 거부될 수 있습니다(추정). 준비 직후의 연결 시험이 이것을 바로 드러냅니다 — ‘넣었지만 키 로그인 거부’.
  • ‘접속 주소 제한(from=)’ 을 켜면 그 노드의 주소가 바뀔 때(주소 변경 · 다른 경로) 키 로그인이 한꺼번에 거부됩니다. 지금 손으로 넣는 안내와 같게 끄는 것을 기본값으로 두었습니다.
  • 계정을 지우거나 넣은 키를 거두는 단추는 넣지 않았습니다(지우는 명령 안내만). 넣은 줄 끝의 주석(vmware-portal-focusmon@노드)으로 찾을 수 있습니다.
  • 같은 주소에 수집 계정이 다른 항목이 둘이면 접속 준비는 계정마다 됩니다(계정별 authorized_keys 라 서로 덮지 않음). 다만 ‘디스크 점검 함께’ 는 v3.17.0 규칙대로 그런 서버에서는 하지 않습니다(sudoers 파일이 서버에 하나).
  • 준비에 쓸 계정의 키 로그인이 거부되면 자동으로 다시 시도하지 않고, 같은 키가 연속 3대 거부되면 10분 동안 그 키를 쓰지 않습니다(v3.17.0 과 같음 — root 계정 잠금 방지).
  • 엣지 서버는 그 엣지 포탈이 이 판 이상이어야 합니다. 실제 RHEL 7 서버에서는 돌려 보지 못했습니다 — 구현 때 이 개발 환경에서 sshd 를 띄워 계정 만들기 · 키 넣기 · 실제 키 로그인까지 돌려 보고, 확인한 것과 못 한 것을 나눠 적겠습니다.
  • 시안의 서버 · 계정 · 키 이름 · 결과는 가상이고, 동시 대수 · 시한은 제안입니다(재지 않았습니다).
