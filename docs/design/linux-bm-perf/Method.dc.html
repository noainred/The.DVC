통합 모니터링 — 서버 1대를 두 경로(OS · iDRAC)로 읽어 엣지에서 한 행으로 합친다
OS(SSH) 는 커널이 보는 것(부하 · 포화 · 프로세스 · 튜닝), iDRAC(Redfish) 는 하드웨어가 보는 것(온도 · 전력 · 부품 · ECC · SMART · 이벤트 로그). 둘 다 법인 엣지가 5분 주기로 읽고, 키(서비스 태그 · host)로 합친다 — 지금 bmusage 가 이미 두 경로를 한 주기에 읽는다.

같은 폴러 한 주기에 두 경로(지금 bmusage poller: iDRAC fetchUsage + osSsh) + 센서 폴러(온도·전력·팬·PSU)·부품 장애 폴러의 최신값을 키로 붙인다. 두 경로의 시각이 다르면 각각의 읽은 시각을 적고, 둘 중 늦은 쪽 기준으로 ‘오래됨’ 을 판정한다.
진단 스냅샷(사람이 누를 때)도 두 경로다 — OS 쪽은 top 프로세스·ss·dmesg, iDRAC 쪽은 최근 SEL/LC 로그·센서 순간값. 원문은 법인 밖으로 나가지 않고 중앙은 봉투만 받는다. 엣지가 없는 법인은 중앙이 직접 붙는 예외(지금과 같다).

근거: `bmusage/usage.js`(CPU·메모리 OS 우선, 출처 srcOf) · `parse/idracTelemetry.js REPORT_KINDS`(system · nic · fc · storage · cpumem) · `idrac/redfish.js`(fetchPower · fetchSensors · LogServices/Sel·Lclog) · `partfault/`. 이 표가 통합 규칙의 단일 원천이 된다(순수 모듈 + 테스트).

교차 판정 — 두 경로가 같이 있을 때만 할 수 있는 것
①CPU 느림의 원인이 전력·열인가 — OS 사용률 97% · 런큐 높음 + iDRAC ‘전력 cap 적용’ 또는 CPU 스로틀링 → “코어 부족이 아니라 cap/열 제한”. 둘 중 하나만 있으면 ‘코어 부족’ 으로 잘못 읽는다.
②디스크 await 급등이 고장 전조인가 — OS await 18ms(평소 0.4) + iDRAC SMART 예측 장애·재할당 증가 → “교체 대상”. SMART 가 깨끗하면 “I/O 양 문제(스냅샷으로 프로세스)”.
③메모리 오류 — iDRAC ECC 정정 카운트 증가 + OS MCE/dmesg → DIMM 슬롯까지 특정. OS 만 있으면 ‘MCE 1건’ 에서 끝난다.
④네트워크 드롭의 층 — OS rx_dropped 증가 · iDRAC CRC 0 → 커널/큐 문제(irq·ring) · iDRAC CRC 증가 → 케이블/광모듈.
교차 판정은 둘 다 읽힌 서버에서만 켜지고, 한쪽이 없으면 “한 경로만 — 원인 특정 불가” 라고 적는다. 상관을 인과로 단정하지 않는다(문구가 ‘후보’ 라고 말한다).

없음등록만 — 행은 있고 칸은 전부 ‘—’이유를 행이 말한다(OS 계정 없음 · iDRAC 등록 없음 · 둘 다 인증 정지)
보드의 KPI 첫 칸이 이 등급 분포다. ‘없음’ 이 많으면 모니터링이 아니라 등록부(bmstor OS 계정 · iDRAC 등록)를 먼저 채워야 한다는 뜻이고, 화면이 그 링크를 준다.
