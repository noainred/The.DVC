## 4. 구조

```
ssh-keys/                         ← <포탈 설정 폴더(CONFIG_DIR)> 아래 · 폴더 0700 · 파일 0600
  <법인>/
    common/<키 이름>(.pub)         ← 법인 공통 키
    servers/<서버>/<키 이름>(.pub)  ← 서버별 키(폴더 이름 = 공용 접속에 등록한 서버 이름)
ssh-access.json                   ← 법인 공통 계정 · 서버(주소 · 포트 · 단독 계정 · 쓰는 키 · 확인 상태) · 비밀 봉인
```

- **계정 · 키를 정하는 순서(코어 하나)**: 서버 단독(계정 · 서버별 폴더의 키) → 법인 공통(계정 · 공통 키) → 없음(‘미설정’ — 접속하지 않는다). 모든 기능이 `resolveSshAccess(법인, 서버)` 하나로 받는다(판정 복제 금지).
- **있는 곳**: 엣지가 있는 법인의 키 · 비밀은 **그 엣지의 설정 폴더**에 둔다(1:1:1 — 그 법인 서버에 붙는 것은 그 엣지다). 중앙은 목록 · 지문 · 공개키 · 확인 상태만 받는다(엣지 로그 pull 과 같은 경로 — 개인키 · 비밀번호는 싣지 않는다).
  엣지가 없는 법인은 중앙 설정 폴더.
- **폴더에 직접 넣은 키**: ‘폴더 다시 읽기’ 또는 주기 확인이 찾아 ‘새로 발견 — 승인 필요’ 로 보인다. 관리자가 승인하기 전에는 쓰지 않는다. 권한(0600 · 소유자)이 다르면 쓰지 않고 이유를 적는다.
- **키 로그인 설정**(서버의 `~/.ssh/authorized_keys` 를 바꾸는 유일한 동작): 비밀번호 접속 → 표식 붙인 공개키 한 줄 추가 → 끊고 키로 재접속 확인 → 실패하면 그 줄 삭제. 비밀번호가 틀리면 다시 시도하지 않는다.
  sshd 설정 · sudoers · 남이 넣은 줄은 건드리지 않는다. 교체는 새 키 확인 뒤에만 옛 줄 삭제.
- **실패도 공용**: 한 기능의 로그인 실패가 그 서버의 자동 접속을 모든 기능에서 멈춘다(`authGuard` 한 벌). ‘다시 확인’ 이나 계정 수정으로 푼다.
- **가림**: 개인키 · 비밀번호는 응답 · 화면 · 로그에 싣지 않는다(지문 · 공개키만). 로드 오류 원문은 `safeLoadText`. 등록부를 못 읽었으면 빈 목록이 아니라 503.
- **권한**: 조회 = 관리자(범위 계정은 자기 법인 · 조회 밖 404) · 계정 수정 · 서버 추가 = 그 법인 쓰기 범위 + 설정 소유자 · **키 만들기 · 가져오기 · 승인 · 삭제 · 교체 · 키 로그인 설정 = 위에 더해 본인 OTP**(`hostaccess` 선례) · 전부 `logAudit`.

## 7. 위험(축소 없이)

- 법인 공통 root 키 하나가 그 법인 서버 전부를 연다. 그래서 S1(법인 단위) · S2(법인 안 보관) · OTP · 감사 로그 · 화면 비노출을 권고했다. 그래도 **엣지 노드가 뚫리면 그 법인 서버 전부가 열린다** — 지금도 엣지는 그 법인 서버의 비밀번호를 받아 쓰므로 새로 생기는 위험은 아니지만, 키는 비밀번호 변경으로 무효화되지 않는다(교체 절차가 그 수단).
- 키 로그인 설정은 서버의 `authorized_keys` 를 바꾼다 — 이 저장소에서 서버 파일을 바꾸는 기능은 변이 검증 · 반증 대상이다(위험한 수정 — 보안 · 자격증명 · 엣지 수신 계약).
- 폴더에 사람이 넣은 키를 자동으로 쓰면 누가 넣었는지 모르는 키로 접속하게 된다 — 그래서 ‘승인’ 을 뒀다.
- 실제 서버에서 `authorized_keys` 권한 · SELinux 문맥 · `AuthorizedKeysFile` 이 기본과 다른 경우를 이 세션에서 확인하지 못했다. 구현 때 가짜 루트 + 실제 `bash` 로 시험하고(`bareos/install` 러너 시험과 같은 방식), 다른 경로를 쓰는 서버는 ‘키 접속 확인 실패 — 더한 줄 삭제’ 로 끝나게 한다.

## 8. 키 보안(원문 ⑤ — 시안 ⑤)

키 하나가 한 법인의 서버 전부를 연다. 그래서 일반 비밀번호 규칙 위에 아래를 더한다.

| 장치 | 무엇을 막나 | 방식 | 끌 수 있나 |
|---|---|---|---|
| 항상 암호화 | 백업 · 사본 · 디스크 유출 | `secretVault` 암호문 형식(AEAD) — 정책이 평문이어도 개인키는 암호화. 평문 파일을 찾으면 ‘키 점검’ 이 경고 | 아니오 |

### 정직 기록 — 한계

- 암호화 열쇠(`secrets-key`)는 포탈(엣지) 서버 안에 있다 — 그 서버의 root 가 넘어가면 키도 열린다(`secretVault.js` 머리 주석이 같은 한계를 밝힌다). ‘잠금 해제 방식’ 만 이 경우를 막고, 대신 재시작마다 수집이 멈춘다.
- 실행 중인 포탈 프로세스 메모리에는 접속하는 동안 개인키 평문이 있다(SSH 라이브러리에 넘겨야 한다). 메모리 덤프까지는 막지 못한다.
- `from=` 제한은 엣지가 NAT 뒤에 있으면 서버가 보는 출발지 주소가 달라 접속이 막힐 수 있다 — 넣은 직후 키 재접속 확인이 실패하면 그 줄을 지우고 ‘제한 없이 다시’ 를 사람이 고르게 한다(자동으로 제한을 빼지 않는다).
- ‘평소와 다름’ 은 표시 · 알림일 뿐 차단이 아니다. 기준(그 사람 · 그 서버 첫 사용, 그 키의 첫 기능)은 단순 규칙이고 오탐이 날 수 있다.
- 두 사람 승인은 관리자 계정이 둘 이상이어야 한다. 한 사람이 계정 둘을 가지면 우회된다 — 계정 관리의 문제로 남는다.
- 이 표의 장치는 **아직 구현 · 시험하지 않았다**(시안). 구현은 위험한 수정 등급(보안 · 자격증명 · 엣지 수신 계약)으로 변이 검증 · 반증을 붙인다.
