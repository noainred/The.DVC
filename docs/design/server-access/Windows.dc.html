Windows 로그인 — 로컬 계정 · AD 계정

Windows 서버에 붙는 길은 다섯 가지입니다. 지금 코드에는 SSH 길과 VM 전용 길만 있습니다. 로컬 계정과 AD 계정은 같은 길로 붙고, 계정명을 적는 법과 확인해 주는 곳만 다릅니다.

확인하지 못한 것 — 이 개발 환경에는 Windows 서버가 없고, 저장소에도 실제 Windows 출력 기록이 없습니다. 아래 Windows 쪽 동작은 공개 문서와 일반 지식에 따른 것입니다. 구현한 뒤 실제 Windows 서버(로컬 계정 한 번 · AD 계정 한 번)로 확인해야 합니다.

방식포트로컬 계정AD 계정서버 쪽 준비포탈 쪽 구현판단

Windows 의 OpenSSH Server		 22됨됨 OpenSSH Server 기능을 켜고 방화벽에서 22 를 연다 새 전송 코드가 없다(Linux 와 같은 SSH). 키 로그인도 된다 1단계

WinRM HTTP + 메시지 암호화 5985됨됨 도메인 환경의 기본 구성에 가깝다 위에 더해 메시지 봉인까지 구현해야 한다. 분량과 위험이 가장 크다 보류

VMware Tools 게스트 작업 vCenter 경유됨됨 VMware Tools 있다 — 게스트 로그인 조사 · GPU 게스트 수집이 쓴다 있음 VM 에만

방식은 법인 기본값으로 정하고 서버마다 바꿀 수 있게 합니다. 1단계는 코드가 이미 있어 실제 서버 확인을 가장 빨리 할 수 있고, 2단계는 OpenSSH 를 켤 수 없는 서버를 위한 길입니다.

같은 계정명이 로컬과 AD 양쪽에 있어도 종류 칸으로 구분합니다. 계정명 표기는 코어가 만들고 기능은 관여하지 않습니다.

WinRM + NTLM 로그인 한 번(2단계)

단계방향내용
1포탈 → 서버TLS 연결. 서버 인증서 지문을 장비 신뢰와 대조한다. 다르면 여기서 끝난다(계정 정보를 보내지 않는다)
2포탈 → 서버협상 메시지. 계정 정보가 없다
3서버 → 포탈도전값(무작위 수)
4포탈 → 서버응답 — 비밀번호에서 만든 값과 도전값으로 계산한 결과. 비밀번호 원문은 보내지 않는다
5서버 안로컬 계정이면 자기 계정 목록과, AD 계정이면 도메인 컨트롤러에 넘겨 확인한다
6포탈 → 서버인증된 연결로 PowerShell 읽기 묶음을 돌리고 출력을 받는다

NTLM 응답은 비밀번호에서 만든 값으로 계산됩니다. 저장된 비밀번호가 새면 그대로 로그인에 쓰이므로 보관이 중요합니다(⑥). NTLM 을 정책으로 꺼 둔 조직에서는 SSH 방식을 씁니다(일반 지식).

방화벽포탈(엣지가 있는 법인은 그 엣지)에서 서버의 22 또는 5986 으로 닿아야 한다방식 표
인증서WinRM HTTPS 는 서버마다 인증서가 필요하다. 사설 인증서면 지문을 설정 › 장비 신뢰에서 승인한다장비 신뢰(지금은 SSH 호스트 키 · TLS 인증서)
AD 계정 잠금틀린 비밀번호를 여러 서버에 보내면 도메인 잠금 정책에 걸려 그 계정 전체가 잠긴다아래 상자
AD 공통 계정이 가장 위험한 지점 — 도메인에서 비밀번호를 바꾼 뒤 포탈에 옛 비밀번호가 남아 있으면, 그 법인 서버에 차례로 시도하는 순간 잠금 횟수를 넘습니다. 그래서 두 가지를 둡니다.
  • 계정 단위 정지 — 로그인 거부가 한 번 나오면 그 공통 계정으로 가는 접속을 모든 서버 · 모든 기능에서 멈춥니다.
  • 한 대 먼저 확인 — 공통 비밀번호를 저장할 때 고른 서버 한 대에서 로그인이 되는지 먼저 보고, 될 때만 나머지 서버에 씁니다.
