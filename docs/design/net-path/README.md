## 1. 요구(사용자 2026-11-26 22:30 KST)

> "VM, 베어메탈 서버가 어디와 통신하고 패킷드랍이나 로스가 어느 구간에서 발생하는지 확인하는 기능 구현 가능 여부 확인하고 시안도 만들어줘"

## 2. 결론 — 가능하다. 단, 세 가지를 구분해야 한다

| 질문 | 판정 | 근거 한 줄 |
|---|---|---|
| **어느 인터페이스에서 패킷이 버려졌나**(구간별 드롭 · 에러 증가) | **가능** — 재료의 절반이 이미 있고 나머지는 기존 수집 경로에 카운터를 더하는 일 | §3 · §4 |
| **어디와 통신하나**(통신 상대) | **조건부 가능** — 게스트/OS 계정이 등록된 서버는 지금 경로로 가능 · 전 서버는 플로우 수신(새 인프라)이 필요 | §5 |
| **이 연결의 패킷이 바로 그 구간에서 버려졌나**(인과 확정) | **카운터로는 불가** — 시각이 겹친다는 사실로 좁힌 *추정* 까지. 확정은 양쪽 동시 캡처(이미 있는 도구) | §6 |

## 4. 구간 모델과 출처 — ‘어디서 버려졌나’

```
① 게스트 NIC ─ ② 가상 NIC ─ ③ 포트그룹/vSwitch ─ ④ 호스트 pNIC(팀) ─ ⑤ 스위치 포트 ─ ⑥ 스위치 사이 ─ ⑦ 스위치 포트 ─ ⑧ 상대 서버 NIC
   (베어메탈은 ①②③④ 대신  ⓑ OS NIC ─ ⑤ 스위치 포트 …)
```

| 구간 | 값 | 출처 | 상태 | 조건 · 한계 |
|---|---|---|---|---|
| ① 게스트 NIC | rx/tx 드롭 · 에러(누적) | 게스트 작업 | **있음** | 게스트 계정이 등록된 VM 만 |
| ② 가상 NIC | `net.droppedRx` · `net.droppedTx`(VM · vNIC 인스턴스별) | vCenter 실시간 통계 | **새로 수집**(기존 QueryPerf 에 추가) | 켜진 VM 전부 · 계정 불필요. vCenter 는 VM 의 에러 수를 주지 않는다 |
| ③ 포트그룹 | 구성(VLAN · 팀)만 | 스냅샷 | 있음 | 카운터 없음 — 화면은 ‘카운터 없음’ |
| ④ 호스트 pNIC | `net.droppedRx/Tx` · `net.errorsRx/Tx`(vmnic 인스턴스별) | vCenter 실시간 통계 | **새로 수집** | VM 이 팀의 어느 업링크로 나가는지는 vCenter API 가 주지 않는다 → 팀 포트를 **모두** 보인다(MAC 표를 읽게 되면 좁힐 수 있다) |
| ⑤⑦ 스위치 포트 | 에러 · **폐기(discards)** 누적 | CVP | 에러 있음 · **폐기 추가** | CVP 에 등록된 Arista 만. 폐기 필드 이름은 실장비 응답으로 확인해야 한다(§7-3) |
| ④↔⑤ 연결(어느 포트에 꽂혔나) | 이웃 정보 → 없으면 스위치 MAC 표 | vCenter `QueryNetworkHint` · CVP | **새로 수집** | 이것이 없으면 스위치 구간을 서버에 붙일 수 없다(상태 B). §7-2 |
| ⑥ 스위치 사이 | — | — | **수집하지 않음** | 패킷이 어느 경로(ECMP · MLAG)로 가는지 포탈이 모른다. 장비 사이 포트의 드롭은 ② 법인 현황 표에 ‘장비 사이’ 로만 나온다 |
| ⓑ 베어메탈 OS NIC | rx/tx 드롭 · 에러 | OS SSH | 에러 있음 · **드롭 추가** | OS SSH 가 등록된 서버만 |
| ⓑ↔⑤ 연결 | iDRAC 스위치 연결 보기 → 없으면 MAC 표 | Redfish(Dell OEM) · CVP | **새로 수집** | §7-4 |
| 법인 사이 회선 | 엣지 간 연결 시험 손실 · RTT | Ping 모니터 | 있음 | 이 서버의 트래픽이 같은 회선을 지나는지는 모른다(상태 C) |

판정은 한 곳(순수 모듈)에서: 누적 카운터는 **두 표본의 차이**(첫 표본 · 리셋 · 간격 초과 = null — `cvp/parse.js portDelta` 와 같은 규칙) · 못 읽음은 0 이 아니라 null(`util/numOrNull.js`) ·
‘증가 없음’ 과 ‘못 읽음’ · ‘수집하지 않음’ 을 **따로 센다**.

## 5. 통신 상대 — ‘어디와 통신하나’

### 5.1 기본안: 게스트 · OS 연결 표 표본(새 인프라 없음)
- VM 은 게스트 작업(`runGuestScript`) · 베어메탈은 OS SSH(`osSsh.js` 의 그 한 번의 명령)에 **연결 표 명령을 더한다**: Linux `ss -tinH`(상대 주소 · 포트 · 연결별 재전송 · 송신 세그먼트 수) · Windows `Get-NetTCPConnection`(상대 · 포트만).
- 표본 사이의 차이로 **상대 × 포트 × 방향** 묶음을 만든다(연결 수 · 재전송 증가 ÷ 송신 세그먼트 증가). 듣는 포트(`LISTEN`)로 들어옴 · 나감을 가른다.
- 한계(시안 문구에 반영): ① 표본 사이에 열렸다 닫힌 짧은 연결은 빠진다 ② UDP 는 대부분 빠진다 ③ **계정이 등록된 서버만**(시안 ② 의 수집 범위 26% · 36% 가 그 모양) ④ Windows 는 연결별 재전송이 없다(‘—’) ⑤ 오래된 커널의 `ss` 는 일부 필드가 없다(없으면 ‘—’).
- 상대 주소는 인벤토리(VM IP · 베어메탈 · IPAM)로 이름을 붙이고, 못 붙이면 ‘등록되지 않은 주소’.

### 5.2 선택안: 플로우 수신(전 서버 · 계정 불필요 · 새 인프라)
- 분산 스위치(VDS) IPFIX 또는 Arista sFlow 를 **법인 엣지**가 UDP 로 받는다. 전 VM · 전 서버의 통신 상대와 바이트 수가 나온다.
- 비용: vCenter(VDS · 포트그룹) · 스위치 설정 변경 · 엣지에 UDP 수신 포트 개방 · IPFIX/sFlow 파서 신규 · sFlow 는 1/N 표본 · 표준 vSwitch 만 쓰는 법인은 IPFIX 불가.
- **이 환경에 VDS · sFlow 가 켜져 있는지 이 세션은 모른다** — 컨펌 질문 ②.

### 5.3 선택안: NSX traceflow
- NSX 세그먼트 위의 VM 끼리는 NSX 가 홉별 관측(어느 DFW 규칙에서 버렸는지 포함)을 준다. NSX 를 쓰는 범위에서만.

## 6. 정직하게 밝혀야 하는 것(시안 문구에 반영)

1. **카운터는 ‘그 인터페이스가 버린 패킷 수’ 다.** 그 패킷이 이 연결의 것인지는 알 수 없다 → 화면의 판정 문구는 ‘드롭이 관측된 곳’ · ‘시각이 겹친다는 사실로 좁힌 추정’ 이고, ‘원인’ 이라고 쓰지 않는다.
2. **재전송은 ‘경로 어딘가의 손실’ 신호일 뿐 위치가 아니다.** 상대 서버의 처리 지연으로도 오른다(상태 E).
3. **읽지 않은 서버는 ‘드롭 없음’ 이 아니다** → 법인 현황 맨 위에 수집 범위(구간별 읽은 수/전체)를 둔다.
4. **vCenter 실시간 통계의 드롭은 누적이 아니라 20초 표본별 합이고 호스트가 약 1시간만 보관한다**(`contention/parse.js REALTIME_INTERVAL = 20` · `vmseries/counters.js REALTIME_MAX_SAMPLES = 180`) → VM · 호스트마다 **1시간 안에 다시 읽어야** 빈 구간이 없다. 못 지킨 구간은 ‘못 읽음’ 으로 남긴다(0 으로 메우지 않는다). 과거 롤업에는 이 카운터가 통계 수준 설정에 따라 없을 수 있다(⚠ 추정 — §7-1).
5. 팀 업링크 · 스위치 사이 · 법인 사이 회선은 위 표의 한계 그대로 화면에 쓴다.
6. 시안의 수치 · 이름은 전부 가상이다. ‘읽은 곳’ 열의 시각 · 수집 범위 숫자는 API 값으로 채운다(화면에 박지 않는다).

## 7. 확인하지 못한 것 — 구현 첫 단계에서 실장비로 확인(⚠ 전부 이 세션의 기억 · 추정)

1. vCenter 카운터 키 `net.droppedRx.summation` · `net.droppedTx.summation`(VM · 호스트) · `net.errorsRx/Tx.summation`(호스트)가 이 환경의 `perfCounterMap` 에 있고 인스턴스별(vNIC 키 · vmnicN)로 오는지 — 목 서버로는 확인할 수 없다. 과거 롤업 보관 여부(통계 수준 2 이상이어야 한다는 것은 기억 기준).
2. `HostNetworkSystem.QueryNetworkHint` 가 주는 이웃 정보: 표준 vSwitch 는 CDP 만 · VDS 는 LLDP 설정 시. Arista 는 LLDP 만 보낸다(기억 기준) → **표준 vSwitch + Arista 조합이면 이웃 정보가 비고 MAC 표 폴백이 주 경로**가 된다.
3. CVP 의 폐기 카운터 필드 이름(`inDiscards` · `outDiscards` 추정) · MAC 표 경로(`/Smash/bridging/…` 추정) — `cvp/client.js` 의 실장비 주석이 보여 주듯 경로 · 필드는 EOS · CVP 버전마다 달랐다.
4. iDRAC 의 스위치 연결 보기(Redfish Dell OEM `DellSwitchConnection` — iDRAC9 기억 기준) · 펌웨어별 제공 여부.
5. `ss -ti` 의 재전송 · 세그먼트 필드가 운영 중인 OS 버전(RHEL 7 계열 포함 여부)에서 나오는지.

→ 그래서 1단계 첫 작업은 **‘통신 점검’ 식의 탐침**(법인 하나에서 위 다섯을 읽어 무엇이 오는지 표로 보이는 진단 화면 또는 스크립트)이다. 탐침 결과에 따라 2 · 3단계 범위가 달라진다.

## 8. 구조(운영 환경 규칙 반영)

- **수집은 법인 쪽**(엣지 → 로컬 vCenter · CVP · 게스트 · OS) · 중앙은 **요약만** 받는다(2026-11-01 규칙). 서버 수만큼 WAN 을 왕복하지 않는다.
- vCenter: 기존 인벤토리 주기의 QueryPerf 묶음에 카운터 2~4개를 더한다 — 로그인 추가 없음 · 시간 예산 · 오래된 것부터(§6-4 의 1시간 안에 한 바퀴가 도는지 법인 최대 VM 수로 산수를 테스트가 고정).
- 게스트 · OS: 기존 조사 주기 · 기존 세션에 명령을 더한다. 인증 실패는 주기 수집을 멈춘다(`util/authGuard.js` — 상태 F) · 자동 재시도 금지.
- 적재: **0 이 아닌 증가분 + 주기별 ‘읽음/못 읽음’ 표지**만(전 인터페이스 × 전 주기를 쌓지 않는다) · 통신 상대는 상대 × 포트 × 방향 묶음의 5분 칸 · 트랜잭션 · `ts` 인덱스 · 청크 prune(`docs/rules/perf-db.md`).
- 엣지 push: 새 필드는 gzip · 청크 · **중앙 정제 화이트리스트** 등재 · 0건이어도 상태를 올린다(`docs/rules/edge.md`).
- 권한: 통신 상대는 민감하다(누가 어디에 붙는지) → adminOnly + 법인 범위(`scopedVcenterIds`) · 범위 밖 404 · 비관리자 판본에는 싣지 않는다. 도구 키 후보 `net-path`(특수기능 › 네트워크) · `toolcats/catalog.js` PRESET 배치.
- 기존 화면은 지우지 않는다: ‘네트워크 이슈 분석’(게스트 NIC) · ‘트래픽 분석’(캡처)은 그대로 두고 새 화면이 그 기록을 읽고 서로 링크한다.

## 11. 컨펌 질문

1. **범위**: 0 → 1 → 2 → 3 순서로 전부(기본) / 1단계까지만 먼저 / 통신 상대(2)를 먼저.
2. **환경**: ① 법인들이 분산 스위치(VDS)를 쓰는가, 표준 vSwitch 인가 ② Arista(CVP 등록)가 전 법인에 있는가 ③ NSX 를 쓰는 범위 — 답에 따라 3단계 주 경로(이웃 정보 vs MAC 표)와 선택안의 실익이 갈린다.
3. **통신 상대 방식**: 연결 표 표본(기본 — 계정 등록된 서버만) / 플로우 수신까지(전 서버 · 설정 변경 필요).
4. **통신 상대 표본 주기**: 5분(기본 — 게스트 작업 부하와 짧은 연결 누락 사이) / 1분 / 15분.
5. **탐침을 돌릴 법인**: 지연이 낮고 Arista · 베어메탈이 다 있는 법인 하나.
6. **메뉴**: 특수기능 › 네트워크에 새 도구 ‘통신 경로 · 손실 구간’(기본) / 기존 ‘네트워크 이슈 분석’ 을 이 화면으로 대체.
