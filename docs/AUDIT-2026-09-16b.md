# 보안 감사 — 인증·인가 게이트 전수 (v2.536, 2026-09-16)

1차(v2.535, `docs/AUDIT-2026-09-16.md`)는 **자격증명·비밀 추적** 한 축만 봤다. 이번 2차는 사용자
지시로 축을 바꿔 **"라우트마다 게이트가 실제로 존재하고 실제로 집행되는가"** 를 전수로 봤다.

**결과: critical 0 · high 1 · medium 0 · low 1 — 2건 모두 수정.**

## 방법 — grep 이 아니라 실제로 띄워서 봤다

1. `src/routes/**` 의 라우트 선언 **763개**를 기계적으로 추출하고, 각 선언의 **미들웨어 체인**을 떼어
   가드 유무를 판정했다(`requirePerm`/`requireRole`/`adminOnly`/`canEdit` 등 **별칭까지 해석** —
   별칭을 못 읽으면 멀쩡한 라우트를 결함으로 오판한다. 초판 스크립트가 실제로 `canProvision`·
   `canEdit` 를 놓쳐 **거짓 양성 40여 건**을 냈다).
2. 후보는 **파일을 열어** 판정했다. 마운트 수준 가드(`router.use(...)`)와 라우터 자체의 마운트
   미들웨어(`app.use('/api/svcmon', …, requirePerm('svcmon'), …)`)는 선언 줄에 안 보이므로
   이 단계가 없으면 틀린다.
3. 확정 결함은 **실제 express 앱에 진짜 라우터를 마운트해 상태코드로 증명**했다. 소스 문자열
   검사는 미들웨어 순서가 바뀌어도 통과한다(v2.506 이 겪은 실패).

## [high] 인벤토리 권한 `inv.*` 6종이 서버에서 **한 번도** 집행되지 않았다

| | |
|---|---|
| 위치 | `routes/api/inventory.js`(hosts·vms·datastores·networks·alarms) · `routes/api/overviewNsx.js`(nsx) · `routes/api/vmMetrics.js` · `routes/api/toolsCapacity.js` |
| 사실 | `PERMISSION_CATALOG` 의 '인벤토리' 그룹 6개(`inv.hosts`·`inv.vms`·`inv.datastores`·`inv.networks`·`inv.nsx`·`inv.alarms`)를 설정 › 사용자 관리가 **체크박스로 켜고 끄게 하는데**, `requirePerm('inv.…')` 를 쓰는 곳은 **알람 음소거 쓰기 2곳뿐**이었다(`grep -rn "requirePerm('inv\." src/` = 2건). 실제로 쓰이던 자리는 `web/src/App.jsx:51-58` 의 **탭 표시 조건** — 즉 **클라이언트 전용 접근제어**다. |
| 실측 | 목 스냅샷(vms 2,242 · hosts 186 · ds 38)에서 `viewer` 권한을 `dashboard` 하나로 줄이고 호출: `/api/vms` **200 · 500건**, `/api/hosts` **200 · 186건**, `/api/datastores` **200 · 38건**, `/api/networks` **200 · 33건**, `/api/alarms` **200 · 58건**, `/api/nsx` **200**, `/api/vcenters` **200 · 11건**. 같은 하니스에서 `/api/tools/storage` 는 **403** — 게이트가 있는 경로는 막히므로 하니스가 아니라 **게이트가 없던 것**이다. |
| 영향 | 관리자가 "이 역할에는 VM 목록을 주지 않겠다" 고 설정해도 **API 는 그대로 답한다.** 화면에서 탭만 사라지므로 관리자는 막혔다고 믿는다 — 무음 실패. 노출되는 것은 VM 이름·IP·게스트 OS·전원 상태, 호스트·데이터스토어·네트워크 목록, 알람 전량이다. |
| 계열 | v2.480(중계 주소가 `/proxies` 에만 게이트) · v2.506(svcmon 조회 6개 무가드)과 **같은 유형**. 세 번째 재발이다. |

**조치** — 서버가 집행한다. 키는 프론트 탭의 `perm` 과 **글자 그대로 동일**하게 맞췄다
(다르면 '메뉴는 보이는데 API 는 403' 이 되어 사용자가 장애로 오해한다 — v2.506 실제 경험).

- **집계(`/summary`·`/overview`·`/compare/matrix`·`/top`·`/vcenters`)는 `dashboard` 수준으로 남겼다** —
  개수·합계만 주고 이름·IP 를 주지 않는다. 조용히 둔 것이 아니라 코드 주석과 이 문서가 그 경계를
  밝힌다. 더 좁히려면 별건으로 다룰 것(대시보드가 통째로 빈다).
- **기본 매트릭스는 operator·viewer 모두 `inv.*` 6종을 전부 갖는다** → 기본 설치는 **동작 불변**

- 화면은 이미 403 을 `AccessDenied` 로 바꾼다(v2.398). Chromium 으로 확인 — '필요한 권한:
  inv.vms 권한' · '설정 › 기능 권한 매트릭스에서 …' · 복사용 요청 문구까지 정상,
  `오류: forbidden` 생노출 없음.

## [low] `/remote/targets` 게이팅 비대칭

| | |
|---|---|
| 위치 | `routes/remote.js` |
| 사실 | 형제 `GET /remote/proxies` 는 v2.480 에 "중계 주소는 원격접속 권한자에게만" 이라며 `requirePerm('remote.access')` 를 받았는데, **`/targets` 는 빠졌다.** 이 경로는 VM 이름·게스트 OS·전원 상태·**모든 IP** 를 돌려준다. |

## 준수 확인 — 의심했다가 **직접 열어 보고 아님을 확인**한 것

거짓 사유는 무음 실패보다 나쁘다(v2.506 교훈). 아래는 전부 실제로 읽고 확인한 것이다.

- **vCenter 범위(scope)는 정상 동작한다.** 실측: scope 제한 계정이 `/api/vms` 에서 2,242건 중
  **240건 · vCenter 1개**만 받았고 `/api/vcenters` 는 11→1건이었다.
  ⚠ **정정** — 처음에는 "scope 도 안 먹는다" 고 판단했는데, **내 하니스가 `scope.vcenterIds` 를
  썼기 때문**이었다(실제 키는 `auth/scope.js` 의 `scope.vcenters`). 제품 결함이 아니라 **내
  테스트의 오류**였고, 키를 고치자 정상 동작했다. 축 자체는 건드리지 않았다.
- **중앙 토큰 라우터(`/api/central/*`) 42개** — 선언 줄에 가드가 없는 것은 `centralRouter.use()`
  토큰 미들웨어가 앞단에 있기 때문이다. 쓰기 8개(`register-collector`·`result`·`fleet`·
  `idrac-scan-progress`·`idrac-scan-result`·`agent-config`·`capture-result`·`bmstor-result`)를
  전부 열어 봤고 **모두 소유권 검증이 있다** — `reqAgentDenied(reqId 소유 엣지)` 또는
  `req.centralAuth.agent || body.agent`(개별 토큰이면 토큰 해석값이 이긴다). `bmstor-result` 는
  **잡에 할당된 서버 id 로만** 반영해 남의 서버 수치 위조까지 막는다.
- **`/metrics`(Prometheus)** — 토큰 미설정이면 **404**, 무인증 공개는 `METRICS_ALLOW_ANON=true`
  옵트인, 쿼리 토큰은 별도 옵트인. 정상.
- **`GET /api/admin/tool-categories` 가 adminOnly 가 아닌 것** — 의도이고 파일 머리말이 사유를
  적고 있다(도구 키와 카테고리 이름뿐, 권한 판정은 `auth/toolAccess.js` 가 한다). PUT 은 adminOnly.
- **`capacityRouter`** — `capacityRouter.use(adminOnly)` 로 **라우터 전체**가 admin 이다.
- **상태변경인데 `requirePerm` 단독인 17개** — v2.500 M-1(viewer 기본 권한이 유일한 게이트) 재발을
  의심했으나, **전부 `tools`·`remote.access` 로 operator 수준**이고 viewer 기본 권한은 하나도 없다
  (`DEFAULT_MATRIX` 상 operator = 조회 + 도구 + 상태 변경). 대표적인 두 개를 열어 확인:
  `POST /vms/upgrade-tools` 는 **쓰기 범위**(`writeScopedVcenterIds`)로 범위 밖 VM 을 걸러내고,
  `DELETE /remote/mappings/:id` 는 **소유자 검사**(소유자 없는 매핑은 admin 전용)를 한다.
- **svcmon 쓰기 30여 개** — `canEdit`(`routes/svcmon/shared.js`)가 붙어 있고 마운트 자체가
  `requirePerm('svcmon')` 아래다(v2.506).

## 보지 않은 것 (정직 기록)

- **실제 운영 배포에서 확인하지 못했다.** 모든 실측은 이 환경의 목(mock) 스냅샷 + 자체 하니스다.
- **권한 매트릭스를 실제로 저장한 현장 파일**(`permissions.json`)이 어떤 상태인지 모른다.
  `inv.*` 를 뺀 역할이 실제로 있는 현장에서는 이 릴리스 이후 그 역할의 화면이 **비게 된다** —
  그것이 관리자가 의도했던 설정이지만, 지금까지 안 막혔으므로 **체감 변화가 있을 수 있다.**
- 인증(세션·토큰·OTP) 자체의 암호학적 검토는 이번 축이 아니다(v2.322·v2.500 감사 범위).
- `insights`·`ping`·`upgrade` 라우터의 **응답 본문**이 권한 수준에 맞는지는 라우트 가드만 봤고
  필드 단위로는 보지 않았다.

## 회귀 테스트

`server/test/authzGates2536.test.js`(4건) — **실제 `api` 라우터를 express 에 마운트**하고
실제 `permissions.json` 을 읽혀 상태코드를 본다(소스 grep 아님).

1. `inv.*` 를 뺀 역할은 9개 경로가 **403 + `requiredPerm`** 이어야 한다(`requiredPerm` 이 없으면
   화면이 `AccessDenied` 대신 범용 오류로 퇴화한다).
2. 기본 권한에서는 **막히지 않는다**(과차단 방지). 동시에 `tools` 없는 역할은 `/tools/*` 가 403 —
   게이트가 살아 있다는 대조군.
3. **서버 게이트 키 == 프론트 탭 `perm` 키**(주석을 제거한 뒤 검사한다).
4. `/remote/targets` 의 `remote.access`.

⚠ 이 테스트는 **변이 검증**을 했다 — `/vms` 의 가드를 일부러 떼면 1번이 실패한다(확인함).
떼도 통과하는 테스트는 테스트가 아니다.
