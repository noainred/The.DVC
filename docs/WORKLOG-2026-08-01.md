## 2. v2.196.0 — 기능별 권한 매트릭스 + 데이터 범위

### 왜
기존 권한은 `admin`/`operator`/`viewer` 3역할뿐이라 "쓰기는 operator 이상" 수준의 **거친 통제**만
가능했습니다. "이 사람은 특수기능은 되지만 원격접속은 막고 싶다" 같은 요구를 표현할 수 없었고,
모든 계정이 전 세계 28개 vCenter를 다 볼 수 있었습니다.

### 무엇을
- **기능 권한 키 17종**을 정의했습니다(대시보드, 인벤토리 6종, 특수기능, 인사이트, 원격접속,
  원격콘솔, VM 사양변경/프로비저닝, 게스트계정 배포, 설정, 업그레이드, 사용자관리).
- **설정 › 사용자 관리**에 역할 × 기능 **체크박스 표**를 추가해 관리자가 직접 켜고 끕니다.
- **서버가 진실의 원천**: `requirePerm(key)` 미들웨어가 라우트를 막고, 브라우저 SSH/RDP
  게이트웨이도 같은 권한으로 검사합니다. 화면에서 메뉴를 숨겨도 API 직접 호출은 차단됩니다.
- **사용자별 데이터 범위(scope)**: 계정마다 볼 수 있는 vCenter/리전을 지정합니다
  (예: 폴란드 법인 계정은 유럽만). 호스트·VM·스토리지·네트워크·알람 목록과 vCenter 필터가
  서버에서 제한됩니다.
- **admin은 항상 전체 권한**이라 매트릭스로 낮출 수 없습니다(관리자 잠김 방지).

### 안전장치
기본 매트릭스를 **기존 role 동작과 똑같이** 맞춰서, 이 기능을 도입하는 것만으로는 아무 권한도
바뀌지 않습니다(무회귀). 매트릭스는 `permissions.json`에 원자적으로 저장되고 손상 시 보존됩니다.

## 8. v2.204.0 — 고권한 계정 OTP 전용 로그인

### 왜
"admin·operator·최고 관리자는 OTP만 쓰고, 데모 계정은 비밀번호를 쓰게 해달라"는 요청입니다.
비밀번호는 유출·재사용 위험이 크고, 고권한 계정일수록 2단계 인증이 필수입니다.

### 무엇을
| 계정 | 비밀번호 로그인 | OTP 로그인 |
|---|---|---|
| admin / 최고 관리자 | ❌ 차단 | ✅ |
| operator | ❌ 차단 | ✅ |
| viewer / 데모 | ✅ 허용 | ✅ |
| AD 계정 | AD 인증 체계(대상 아님) | — |

비밀번호가 **맞아도** 고권한 계정은 서버가 403 + "OTP 등록 필요" 안내로 거부합니다
(무차별 대입 잠금 카운터에는 넣지 않고, 감사 로그에는 남깁니다).

### ★ 가장 중요한 설계 — 초기 구축 잠금 방지
비밀번호 로그인을 무조건 막으면 **첫 설치에서 아무도 로그인할 수 없어 OTP를 등록할 방법 자체가
사라집니다**(전체 잠김). 그래서:

1. **아무 admin도 OTP를 등록하지 않은 동안**은 admin 비밀번호 로그인을 허용(유예).
2. **admin 한 명이라도 OTP를 등록하면 유예 자동 종료** → 전 고권한 계정에 정책 적용.
3. operator는 유예가 없으므로 admin이 QR을 발급해 전달.
4. 마지막 admin이 OTP를 해제하면 유예가 자동으로 되살아나 복구 가능(잠김 없음).
5. 긴급 시 `OTP_ROLE_ENFORCE=false`로 정책 자체를 끌 수 있습니다.

> ⚠️ **이 유예 방식은 v2.205~v2.206에서 폐기되었습니다.** "유예 중에는 비밀번호가 통한다"는
> 것 자체가 공격 창이라, 아래 9·10장의 **계정 단위 부트스트랩 + 강제 등록 + 비번 삭제**로
> 바뀌었습니다. 현재 동작은 10장을 기준으로 보세요.

## 9. v2.205.0 — 유예 폐기 + 콘솔 등록 도구

### 왜
"admin·operator는 **무조건** OTP만 쓰고 비밀번호는 아예 못 쓰게 해달라"는 재확인 요청이었습니다.
v2.204의 전역 유예(아무도 OTP를 등록 안 했으면 비번 허용)는 **설치 직후~첫 등록 사이**가
통째로 비밀번호 로그인 구간이라, 그 구간을 노리면 정책이 무의미했습니다.

### 무엇을
- 전역 유예를 **제거**하고, admin·operator는 예외 없이 비밀번호 로그인을 거부하도록 바꿨습니다.
- 대신 **콘솔(서버 터미널) 등록 도구**를 새로 만들었습니다 — 화면 로그인 없이 OTP를 등록하는
  유일한 경로이자, "모든 admin이 OTP를 분실"한 잠금 상황의 복구 수단입니다.

```bash
npm run otp-enroll -- --list          # 계정 목록·등록 여부 확인
npm run otp-enroll -- admin           # QR(텍스트) + 수동 입력 키 출력
npm run otp-enroll -- admin --confirm 123456   # 6자리로 확정
npm run otp-enroll -- admin --disable # 등록 해제
```

- 서버 기동 시 **OTP 등록된 admin이 하나도 없으면 경고 로그**로 절차를 안내합니다.

### 남은 문제
콘솔 접근이 불가능한 환경(원격 SaaS·위탁 운영)에서는 첫 관리자 진입 자체가 막힙니다 →
v2.206에서 온보딩 흐름으로 해결했습니다.

## 10. v2.206.0 — ★ 최초 설치 온보딩 (현재 정책)

### 왜
"완전 처음 설치할 때는 admin 비밀번호를 설치 경로에 **랜덤하게 저장**하고, 처음 로그인할 때
그 **파일 경로를 팝업**으로 띄우고, 비밀번호로 로그인하면 **무조건 OTP를 등록**하게 하고,
OTP를 등록하면 **비밀번호를 삭제**하라"는 요청입니다. 보안(OTP 전용)과 실사용(첫 진입 가능)을
동시에 만족시키는 최종 형태입니다.

### 무엇을 — 3단계
| 단계 | 동작 |
|---|---|
| ① 부트스트랩 | **OTP 미등록 계정만** 비밀번호 로그인 허용(최초 설치·계정 발급 직후 한정). 비밀번호는 설치 시 랜덤 생성되어 `initial-admin-password.txt`(0600)에 저장 |
| ② 강제 등록 | 그 세션에는 `mustEnrollOtp` 표식이 붙고, **OTP 등록 관련 3개 API를 뺀 모든 API가 403**(`requireEnrolled`). 화면도 등록 전용 화면(QR+수동키+6자리)에 고정 |
| ③ 비번 폐기 | 등록을 확정하면 서버가 **비밀번호 해시를 삭제**하고 토큰을 전부 폐기. admin이면 `initial-admin-password.txt`도 함께 삭제 → 이후 비밀번호 경로 자체가 소멸 |

- 로그인 화면은 **초기 구축 중에만** 비밀번호 *값*이 아닌 **파일 경로**를 팝업으로 안내하고,
  등록이 끝나면 안내가 사라집니다.
- `mustEnrollOtp`는 토큰이 아니라 **매 요청 사용자 레코드 기준**으로 계산돼, 등록 즉시 반영되고
  낡은 토큰으로 우회할 수 없습니다.

### 콘솔 도구 개선 (실사용 피드백 반영)
리눅스 설치본에는 npm이 없어서 `npm run otp-enroll`을 쓸 수 없었고, `sudo node ...`로 돌리면
`users.json`이 **root 소유가 되어 포탈이 못 쓰는** 부작용이 있었습니다. 그래서 래퍼 스크립트를
만들고 설치 시 심볼릭 링크를 겁니다:

```bash
sudo vmware-portal-otp --list
sudo vmware-portal-otp admin
```

래퍼가 **번들 Node 경로 · `CONFIG_DIR` · 서비스 계정(`vmportal`) 강등**을 알아서 처리합니다.

전체 소스를 다시 훑어 **직접 만든 신기능의 빈틈 3건**을 찾아 고쳤습니다.

| # | 문제 | 왜 위험한가 | 수정 |
|---|---|---|---|
| 1 | **WS 게이트웨이가 `mustEnrollOtp`를 안 봄** | SSH/RDP 터널은 Express 미들웨어를 타지 않아 `requireEnrolled`가 적용되지 않음 → **OTP 등록 전 세션으로 서버 터널을 열 수 있었음** | upgrade 핸들러 안에서 인증·권한·등록여부를 직접 검사 |

## 12. v2.208.0 — 설정 접근 계정을 '파일'로

### 왜
설정 소유자를 포탈 UI에서만 지정할 수 있으면, **전원이 목록에서 빠지는 순간 아무도 설정에
못 들어가는 영구 잠금**이 발생합니다(복구 경로 없음). "특정 사용자만 설정을 볼 수 있도록
서버 파일로 관리해달라"는 요청과 맞물린 문제였습니다.

### 무엇을
유효 소유자 = **다음 4가지의 합집합**입니다.

1. 포탈 UI 저장분(설정 › 세션 보안)
2. `$CONFIG_DIR/settings-owners.txt` — 한 줄에 계정 하나, `#` 주석 가능
3. `portal.env`의 `SETTINGS_OWNERS=계정1,계정2`
4. 중앙 배포 admin + 수퍼관리자 `noainred`(항상 자동 포함)

2~4는 UI 저장분에 기록되지 않으므로 **UI에서 지울 수 없습니다** → 잠금 사고의 복구 경로.
설치 스크립트가 예시 파일(0600)을 만들어 둡니다.

### 함께 처리 — [비번 설정] 버튼 숨김
사용자 관리 목록의 **[비번 설정]** 버튼이 `admin`·`operator` 계정에도 보여 혼란스러웠습니다
(OTP 전용이라 비밀번호를 설정해도 로그인에 쓸 수 없음). 이제 **비밀번호 로그인이 가능한
계정에만** 표시합니다.

## 13. v2.209.0 — 특수 기능 탭 상시 노출

### 왜
특수 기능 도구가 45개나 되는데, 권한이 없으면 **상단 메뉴 자체가 사라져** 사용자가
"기능이 없는 건지, 권한이 없는 건지" 알 수 없었습니다.

### 무엇을
- 상단 **'특수 기능' 탭은 항상 표시**합니다.
- 권한 있는 도구 = 정상 색상·클릭 가능 / 권한 없는 도구 = **회색 + 클릭 불가**.
- 잠긴 도구에는 **사유**를 붙입니다 — "관리자(admin) 전용" 또는 "접근 권한 없음 —
  관리자에게 요청(설정 › 사용자 관리 › 특수 기능 도구별 접근)".

"메뉴가 안 보인다"는 문의가 "권한을 요청하면 되는구나"로 바뀌는 UX 개선입니다(서버측 차단은
그대로 유지 — 표시만 바뀌고 권한은 그대로).

## 14. v2.210.0 — 5차 보안 감사: 백업 = 자격증명 사본

### 왜 (실제 발견된 취약점)
포탈 백업 아카이브에는 `portal.env`(**AUTH_SECRET**·`CENTRAL_TOKEN`) · `users.json`(**TOTP
시크릿**·비번 해시) · `vcenters.json` 등 **전 자격증명의 사본**이 들어갑니다. 그런데 UI는
'설정' 탭을 소유자 전용으로 가려 놓았지만 **API는 단순 `adminOnly`** 였습니다 →
소유자가 아닌 admin이 API를 직접 호출해 통째로 인출할 수 있었습니다.

`AUTH_SECRET`이 유출되면 **임의 계정(수퍼관리자 포함)의 토큰을 위조**할 수 있어,
공들여 만든 OTP 전용 정책과 소유자 경계가 **동시에** 무너집니다.

### 무엇을
- `/api/admin/backup/*` **7개 라우트 전부**와 `GET /security/session`에 `requireSettingsOwner`
  적용(기존에는 PUT만 소유자 전용이었음).
- 백업 **다운로드·복원에 감사 로그**를 남깁니다(누가 자격증명 사본을 꺼냈는지 추적).
- 백업 대상 확장자 화이트리스트(`.json`/`.env`)를 **넓히지 말 것**을 규칙으로 못박았습니다 —
  넓히면 `settings-owners.txt`가 복원 대상이 되어 **소유자 목록을 갈아끼울 수** 있습니다.
- 회귀 방지 테스트 12건 추가(라우트 선언 줄에 가드가 붙어 있는지 소스 수준에서 검사).
