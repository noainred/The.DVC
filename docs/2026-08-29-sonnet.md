## 조사 개요

- **범위**: git diff가 아니라 저장소 전체 소스 — `server/src/**`, `web/src/**`, `pyportal/**`.
- **방법**: 8개 전문 서브에이전트를 영역별로 나눠 병렬 실행(수집파이프라인/vcenter/인벤토리/리포트, pyportal, 핵심 인프라(store/util/central), 보안 민감 영역(auth/proxy/upgrade 등), IPAM/vmtrack, API 라우트, idrac/metrics/gpu/nsx 폴러, 웹 프론트엔드). 각 에이전트가 `CLAUDE.md`·`server/CLAUDE.md`·`pyportal/CLAUDE.md`에 문서화된 기존 불변조건을 먼저 로드하고, 그 불변조건의 회귀 여부와 **문서화되지 않은 새 정확성 버그**를 함께 찾도록 지시했다.

#### 1. 이중 UTF-8 인코딩 손상이 git에 커밋됨 [재현 확인]
**파일**: `server/src/routes/api/storageMon.js`, `server/src/routes/api/bmstor.js`, `server/src/routes/admin/idracScan.js`, `server/src/routes/admin/collectorsDc.js`, `server/src/routes/admin/deployLlm.js`

역변환 원문: `'서버를 찾을 수 없습니다.'`

`.js` 소스로서는 정상 파싱되므로(문자열 리터럴 자체가 손상 바이트를 담을 뿐 문법 오류는 아님), Node가 이 문자열을 그대로 JSON 응답에 실어 보낸다.

#### 2. WS SSH/RDP 게이트웨이 — `AUTH_ENABLED=false`에서 `ReferenceError` [재현 확인]
**파일**: `server/src/proxy/sshGateway.js:33-45`, `server/src/proxy/guacdTunnel.js:53-63`

```js
if (config.auth.enabled) {
  const user = resolveTokenUser(url.searchParams.get('token'));   // 블록 스코프 const
  ...
}
wss.handleUpgrade(req, socket, head, (ws) => handleConnection(ws, user)); // ← user 미정의
```
`user`는 `if (config.auth.enabled) { ... }` 블록 내부에서만 선언되는데, 블록 밖 `wss.handleUpgrade` 호출에서 참조한다. `AUTH_ENABLED=false`(문서화된 지원 모드)일 때 이 블록이 스킵되어 `user`가 어떤 스코프에도 존재하지 않아 `ReferenceError`가 발생한다 — 서브에이전트가 `node -e` 로 직접 재현 확인.

**영향**: 전역 `uncaughtException` 핸들러가 있어 프로세스는 죽지 않지만, 예외가 `wss.handleUpgrade` 호출 **이전**에 발생하므로 그 HTTP Upgrade 소켓은 절대 처리되지 않고 방치된다 → 반복 연결 시도마다 소켓이 새는 미인증 원격 DoS. 또한 `AUTH_ENABLED=false` 모드에서 `/api/remote/ssh`, `/api/remote/rdp` 기능 자체가 항상 동작하지 않는다(회귀가 아니라 원래부터일 가능성이 높음 — 추정, git blame 미확인).

**추가 설계 노트**: 단순히 `let user;`를 블록 밖으로 끌어올리기만 하면, HTTP 쪽 `requireRole`/`requirePerm`이 `AUTH_ENABLED=false`일 때도 `AUTH_DISABLED_ROLE`을 검사하는 것과 달리 WS 게이트웨이는 그 검사 없이 무조건 접속을 허용하는 상태가 된다. 수정 시 `AUTH_DISABLED_ROLE` 기반 권한 검사도 함께 넣어야 한다.

**영향 범위**: 기본값(`AUTH_ENABLED` 미설정=true)에서는 트리거되지 않음 — 운영자가 이 env를 명시적으로 `false`로 설정한 배포에만 해당.

#### 3. SSH 명령 실행에 타임아웃 없음 → bmstor/GPU 폴러 영구 정지 [코드 분석]
**파일**: `server/src/proxy/sshExec.js:26-36`

```js
function exec(conn, command) {
  return new Promise((resolve, reject) => {
    conn.exec(command, (err, stream) => {
      if (err) return reject(err);
      let stdout = '', stderr = '';
      stream.on('data', (d) => { stdout += d.toString(); });
      stream.stderr.on('data', (d) => { stderr += d.toString(); });
      stream.on('close', (code) => resolve({ command, code, stdout, stderr }));
    });
  });
}
```
`readyTimeout`은 초기 SSH 핸드셰이크만 제한한다. 연결 이후 `exec()`는 원격 셸의 `close` 이벤트만 기다리며, 명령 실행 자체에 타임아웃이 없다.

이 함수는 아무 추가 가드 없이 `bmstor/collect.js`(`df -P -k -- ...`)와 `gpu/sshCollect.js`(`runNvsmi`, `collectVmGpuSsh`)에서 쓰인다.

**트리거**: bmstor 대상의 마운트 포인트가 오래되거나 응답 없는 NFS/CIFS 공유일 때, `df`가 커널에서 무한정 블로킹(D-state, 흔한 실무 장애)할 수 있다 — SSH 연결/keepalive는 정상이고 자식 프로세스만 멈춘다. `exec()`의 Promise가 영원히 resolve되지 않아: `bmstor/collect.js`의 `collectServer`가 반환하지 않음 → `bmstor/poller.js`의 재진입 가드(`running`)가 `finally`에 도달하지 못해 **영구히 true로 고정** → 주기 폴링·수동 "지금 실행" API 모두 프로세스 재시작까지 계속 `{skipped:true}`만 응답. GPU SSH 수집도 동일 패턴(멈춘 `nvidia-smi`가 GPU 폴러 전체를 얼림).

```python
def public_check_cooldown(self) -> int:
    remaining = int(self.public_check_interval - (time.time() - self._last_public_check))
    if remaining > 0: return remaining
    self._last_public_check = time.time()
    return 0
```
다른 모든 공유 상태는 락으로 감싸는데 이 read-then-write는 무보호다. `ThreadingHTTPServer`라 요청마다 스레드가 뜨므로, 여러 스레드가 거의 동시에 호출하면 30초 쿨다운을 짧은 버스트로 우회할 수 있다.

**18. `Notifier.notify_transitions` 락 밖 상태 변경** — `pyportal/hub/notify.py:50-111`. `with self._lock:` 블록은 이벤트 리스트 생성 부분만 감싸고, 이후 `event["entry"]["status"]`, `entry["last_sent"]` 갱신은 락 없이 이뤄진다. 현재는 `GuardedJob`으로 단일화돼 실제 크래시로는 안 보이지만, 클래스의 스레드 안전성 계약 자체가 깨져 있어 향후 다른 경로가 직접 호출하면 즉시 레이스가 된다.

**19. CSV `_unguard`가 사용자의 리터럴 `'=`,`'+` 값을 손상** — `pyportal/hub/csvio.py:41-46`. `_guard`가 붙인 이스케이프 아포스트로피와 사용자가 수식 실행을 막으려 직접 입력한 아포스트로피를 구분할 방법이 없다. `'=1+1`(리터럴 텍스트 의도)을 내보낸 뒤 다시 가져오면 앞의 `'`가 제거되어 `=1+1`로 저장된다.

**20. 백업 파일명 동일초 충돌** — `pyportal/hub/backup.py:40-46`. 초 단위 타임스탬프+reason만으로 파일명을 만들어, 같은 초에 같은 reason으로 `create()`가 두 번 호출되면(버튼 더블클릭 등) 첫 백업이 조용히 덮어써진다.
