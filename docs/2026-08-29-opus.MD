### 정직성 고지 (반드시 읽을 것)

- **실행 검증한 것과 코드 독해로만 판정한 것을 구분해 표기했다.** 각 항목에 `확신도` 열이 있다.
  - `확정` = 코드 경로가 명백하거나 실제로 실행해 재현했다.
  - `높음` = 코드 독해로 결론이 명확하지만 운영 데이터로 재현하지 않았다.
  - `추정` = 조건부로만 발생하며 그 조건 성립을 확인하지 못했다.
- **운영 환경에서 실제로 관측하지 않았다.** 빈도·영향 규모 수치는 코드에서 계산한 것이며 실측이 아니다(계산 근거를 함께 적었다).
- `pyportal` 은 6차 감사까지 이미 수행된 코드이고 `ver.txt` 기준 v2.322 이후 변경이 없다. 이번에는 **패턴 스캔만**(가변 기본인자 · bare except · naive datetime · 락 사용) 했고 **결과는 전부 깨끗했다**. 깊이 있는 로직 감사는 하지 않았으므로 "pyportal 에 버그가 없다"고 말할 수 없다.
- `npm test` / `npm run build` 는 이번 감사에서 **실행하지 않았다**(읽기 전용 감사). 수정 적용 시 반드시 `npm run verify` 로 확인해야 한다.

### B1 — `/api/tools/*` 조회 라우트 95개에 권한 검사 누락 (높음)

**현상.** `/api` 라우터는 `index.js:158` 에서 `authMiddleware, requireEnrolled` 를 전역 적용하므로 **인증**은 강제된다. 그러나 **기능 권한(`requirePerm`)** 은 각 라우트가 개별로 걸어야 하는데, `/tools/*` 라우트 117개 중 **22개만** 권한/역할 가드를 가진다.

```
$ grep -c "api\.(get|post|put|delete)\('/tools/..." server/src/routes   # 전체
117
$ ... ", *require"                                                       # 가드 있는 것
22
```

**근거.** 기본 권한 매트릭스(`server/src/auth/permissions.js:62`)에서 `viewer` 행은 `tools` 를 갖지 않는다.

```js
viewer: [
  'dashboard', 'inv.hosts', 'inv.vms', 'inv.datastores', 'inv.networks', 'inv.nsx', 'inv.alarms',
  'insights', 'vm.console',
],                       // ← 'tools' 없음
```

그런데 다음 조회 라우트에는 가드가 없다(발췌):

| 라우트 | 정의 위치 | 노출 데이터 |
|---|---|---|
| `GET /tools/ipam` | `routes/api/ipamExport.js:69` | IP 관리대장 전량(IP·소유자·OS·호스트·관리상태) |
| `GET /tools/ipam.csv`, `.xlsx` | `ipamExport.js:398`, `:391` | 같은 대장 파일 다운로드 |
| `GET /tools/hardware` | `routes/api/hardwareGpu.js:240` | 서버 모델·**서비스태그** |
| `GET /tools/gpu`, `/tools/gpu.csv` | `hardwareGpu.js:291`, `:309` | GPU 인벤토리 |
| `GET /tools/licenses` | `routes/api/toolsInfo.js:96` | **라이선스 키** |
| `GET /tools/license-expiry` | `toolsInfo.js:122` | 라이선스 키 + 만료 |
| `GET /tools/report/*` (10종) | `routes/api/reports.js` | 컴플라이언스·좀비VM·미보호VM 리포트 |
| `POST /tools/deep-search` | `routes/api/checksLogs.js:37` | 전 인벤토리 통합검색 |
| `GET /tools/snapshots`, `/tools/duplicate-ips`, `/tools/esxi`, `/tools/hba`, `/tools/guest-os` … | 각 모듈 | 인벤토리 상세 |

이는 같은 파일의 자체 주석과 모순된다 — `permissions.js:11` *"서버가 진실의 원천이며(requirePerm), 프론트는 …노출만 한다"*, `auth.js:740` *"서버측 강제 — 프론트가 메뉴를 숨겨도"*.

**영향.** `viewer` 계정 보유자가 브라우저 개발자도구/curl 로 `Authorization` 헤더만 재사용해 위 엔드포인트를 호출하면, UI 에서 숨긴 특수기능 데이터를 전부 받는다. 특히 **라이선스 키**와 **IP 관리대장 전량**은 등급이 다른 정보다.
단, `scopedVcenterIds` 기반 **데이터 범위(scope) 는 각 라우트에서 정상 적용**되므로 "범위 밖 vCenter 유출"은 아니다. 문제는 "권한 없는 기능 접근"이다.

**참작 사항(정직하게).** `viewer` 도 이미 `inv.hosts`/`inv.vms`/`inv.datastores` 를 갖고 있어 호스트·VM·DS 목록 자체는 정당하게 볼 수 있다. 따라서 실질 추가 노출은 **IPAM 대장 · 서비스태그 · 라이선스 키 · 리포트류**로 좁혀진다. 그래도 매트릭스 설계 의도(도구 접근 통제)가 서버에서 무효라는 점은 그대로다.

**수정 방향.**
1. `routes/api.js` 에서 `api.use(['/tools', '/tools/*'], requirePerm('tools'))` 를 register 호출 **앞**에 두어 일괄 강제 — 단 이미 `requireRole('admin')` 인 라우트는 그대로 통과(더 강한 조건이 뒤에 남음).
2. 예외가 필요한 라우트(있다면)만 명시적으로 화이트리스트.
3. 회귀 테스트: `viewer` 토큰으로 `/api/tools/ipam` → 403 을 단정하는 테스트를 `server/test/` 에 추가.

### B2 — 도구별 거부목록(`toolsDenied`)이 서버에서 강제되지 않음 (높음)

**현상.** 관리자가 사용자 관리에서 "특수기능 개별 도구"를 역할별로 **거부**할 수 있다(`permissions.json` 의 `toolsDenied`). 이 값은 **프론트에서만** 검사된다.

**근거.** `roleToolsDenied` 의 전체 사용처:

```
server/src/auth/permissions.js:153   ← 정의
server/src/routes/auth.js:79         ← 로그인 응답에 담아 내려줌
server/src/routes/auth.js:96         ← /auth/me 응답에 담아 내려줌
```

강제하는 미들웨어가 **없다**. 실제 판정은 브라우저에서 한다:

```js
// web/src/api.js:37
export const toolAllowed = (k) => {
  const u = _currentUser;
  if (!u || u.role === 'admin') return true;
  if (!can('tools')) return false;
  const denied = Array.isArray(u.toolsDenied) ? u.toolsDenied : [];
  return !denied.includes(k);
};
```

**영향.** 관리자가 `operator` 에게 `ipam` 도구를 거부해도, 그 계정은 `GET /api/tools/ipam`, `/tools/ipam.csv`, `/tools/ipam/subnets`, `/tools/ipam/netmap` 등을 그대로 호출할 수 있다. `operator` 는 기본 매트릭스에 `tools` 가 **있으므로**, B1 을 고쳐 `requirePerm('tools')` 를 일괄 적용해도 **이 문제는 남는다**(별개 결함).

**수정 방향.**
1. 도구 키 ↔ 라우트 접두사 매핑 테이블을 서버에 두고 `requireTool('ipam')` 미들웨어를 신설.
2. 최소 조치로도, IPAM/하드웨어/GPU/리포트처럼 거부 대상으로 노출되는 도구의 라우트 그룹에 `requireTool` 을 건다.
3. 매핑 누락이 곧 우회이므로, `specialToolsList.js` 의 도구 키 목록과 서버 매핑이 **일치하는지 검사하는 테스트**를 함께 추가할 것(도구 추가 시 서버 매핑 누락 방지).

### B3 — vCenter '비활성/점검중' 전환이 VM 추이에 허위 대량 삭제로 기록됨 (높음, 실행 재현)

**현상.** `takeVmSnapshot` 이 추적할 vCenter 를 고르는 필터는 `unreachable` 과 `pending` 두 상태만 제외한다.

```js
// server/src/vmtrack/service.js:35
const targets = (snap.vcenters || [])
  .map((vc) => ({ id: String(vc.id || ''), status: vc.status }))
  .filter((vc) => vc.id && !(vc.status === 'unreachable' && !(byVc.get(vc.id) || []).length)
    && !(vc.status === 'pending'     && !(byVc.get(vc.id) || []).length));
```

그런데 `store.js` 는 **VM 을 하나도 담지 않은** 항목을 두 가지 더 만든다.

```js
// server/src/store.js:275  — 비활성(enabled === false)
merged.vcenters.push({ id: vc.id, name: vc.name, location: vc.location, status: 'disabled' });

// server/src/store.js:279-296 — 점검중(maintenance)이고 직전 정상 캐시가 없을 때
} else {
  merged.vcenters.push({ id: vc.id, name: vc.name, location: vc.location, status: 'maintenance', maintenance: true });
}
```

두 상태 모두 필터를 **통과**하므로 `diffVcenter([], prevRoster)` 가 호출된다.

**재현(실제 실행).**

```
$ node -e "diffVcenter([], prevRoster)  // roster 3대"
total = 0 / removed = 3 / baseline = false
removed names = A,B,C
totalRow.removed = 3  totalRow.total = 0
```

**영향.** 5,850 VM 규모에서 한 vCenter(예: 200 VM)를 비활성/점검중으로 전환하면 그 슬롯에:
1. `snaps.removed` 에 200 이 기록되고 `total` 이 200 줄어든다 → 추이 차트에 **허위 급락 + `-200대`**.

### B7 — `ds_series` prune 이 DS 의 '첫 관측' 기준선을 지움 (중간)

`ds_series` 는 **diff 압축** 테이블이다 — "첫 관측 + 1GB 이상 변화한 슬롯"만 1행씩 저장하고, 조회 시 마지막 관측값을 이어붙인다(`stepFill`). 그런데 prune 은 단순 시각 절단이다.

```js
// server/src/vmtrack/db.js:421 (보존 1,095일 기본)

```

**영향.** 사용량이 거의 변하지 않는 VMFS 데이터스토어(주석에도 *"대부분의 VMFS 는 사용량이 안 변한다"* 고 적혀 있다)는 `ds_series` 에 **행이 단 1개(첫 관측)** 뿐이다. 보존기간(3년)이 지나면 그 행이 삭제되고:

- `readDsSeries` → `carryIn = null`, `rows = []`
- `stepFill` → 모든 슬롯이 `capGB:null, usedGB:null` → 개별 DS 추이 차트가 **전부 '—'**
- `dsStartValues` → `carry`·`firstIn` 둘 다 없음 → `vmtrackDsTop` 의 `deltaGB` 계산에서 그 DS 가 **탈락**(`startVal == null` → `continue`), `vmtrackDsSeriesAll` 은 `deltaGB = 0`

**시한(정직하게).** 기본 보존 1,095일이므로 기능 도입(v2.353, 2026-08) 기준 **2029년경**에 발현한다. 다만 `VMTRACK_RETENTION_DAYS` 를 낮춘 배포에서는 즉시 문제가 된다.

**수정 방향.** "DS 별 최신 1행은 남긴다"를 prune 에 반영한다.

```sql
DELETE FROM ds_series

   AND ts <> (SELECT MAX(ts) FROM ds_series s2 WHERE s2.ds_id = ds_series.ds_id)
```

`idx_dsseries_ds (ds_id, ts)` 인덱스가 이미 있어 상관 서브쿼리는 인덱스로 처리된다. 같은 원칙이 `pruneVmperf` 의 `pruneHourly(before - HOUR)`(경계 버킷 보존)에 이미 적용돼 있으므로 규약도 일관된다.

### B8 — vmperf DB 파일명 sanitize 충돌 (낮음)

```js

```

`vc:서울` 과 `vc_서울`, 또는 `vc a` 와 `vc-a` 처럼 sanitize 후 같은 문자열이 되는 두 vCenter id 는 **같은 `.db` 파일**을 쓴다.

**조회는 안전하다** — 행의 `k` 컬럼이 원본 `vcenterId` 라서 `(metric, k)` 조회는 섞이지 않는다. 문제는 파일 단위 조작이다:

- `dropVmperfDb(vcenterId)` (`:192`) — 한쪽 vCenter 를 추적 대상에서 빼면 **충돌 상대의 데이터까지 삭제**된다. 이 파일 삭제가 v2.376 이 vCenter 별 DB 를 분리한 **핵심 이유**(용량 즉시 회수)라 실제로 호출되는 경로다.
- `vmperfDiskUsage()` (`:203`) — 파일명 → `vcenterId` 역변환이 불가능해 화면에 **엉뚱한 vCenter id** 로 용량이 표시된다.

한글·공백을 쓰는 vCenter id 가 실제로 있는지는 확인하지 못했다(`vcenters.json` 미열람). v2.388 이 "특수문자 vCenter id 데이터 유실"을 고쳤다는 릴리스 노트가 있으므로 특수문자 id 는 현장에 존재한다고 보는 편이 안전하다.

**수정 방향.** sanitize 결과에 **원본 id 해시 접미사**를 붙여 단사(injective)로 만든다.

```js
const safe = raw.replace(/[^A-Za-z0-9._-]/g, '_').slice(0, 100);
const tag  = crypto.createHash('sha1').update(raw).digest('hex').slice(0, 8);
return `${safe || 'vc'}-${tag}`;
```

기존 파일 호환을 위해 "새 이름이 없고 옛 이름이 있으면 옛 이름 사용" 폴백을 한 릴리스 유지할 것.

### B18 — `syncLedger` 동시 실행 가드 없음 (낮음, 추정)
